# 检索架构与推荐链路技术说明

## 1. 文档目的

本文用于解释项目从早期 GraphRAG/Hybrid 检索到当前受控检索架构的演进，以及一次请求在意图识别、实体解析、图查询、PDS 元数据过滤、Milvus 召回、重排和最终生成之间如何流转。

本文描述的是当前仓库中已经实现或已经通过验收的路径。项目仍保留旧的 Hybrid/GraphRAG 路径作为兼容和回退能力，因此“新路径”和“旧路径”需要区分理解。

## 2. 一句话概括

旧方案是“让 LLM 判断怎么搜，再把检索结果交给 LLM 生成”。

新方案是“让 LLM 只理解用户需求，本地程序按固定契约选择检索路线；硬约束先缩小范围，Milvus 在范围内召回，软偏好负责重排，PDS 返回可信正文，证据不足时安全停止”。

核心分工可以记成：

```text
Neo4j：确认实体和关系是否存在
PDS：保存版本化父文档、元数据和正文回补能力
Milvus：在受限范围内进行向量相似度召回
Reranker：根据软偏好调整候选排序
LLM：理解需求并基于证据生成最终回答
```

## 3. 旧方案与新方案

### 3.1 旧方案

早期链路大致如下：

```text
用户问题
  ↓
LLM 分析复杂度、实体数和关系强度
  ↓
LLM 选择 Hybrid 检索或 GraphRAG 检索
  ↓
向量片段、图节点或图关系被拼成上下文
  ↓
LLM 生成答案
```

旧方案的问题主要包括：

- LLM 同时承担意图理解、检索路线选择和部分执行决策，权限边界较宽；
- 不同问题没有统一的输入契约，检索路径容易受模型输出格式影响；
- 图节点和向量片段临时拼接正文，全文、章节和步骤边界不稳定；
- 实体不存在、关系不存在和服务不可用时，容易退化为宽泛检索或让模型继续猜测；
- “必须满足”和“尽量满足”缺少统一的硬约束/软偏好划分；
- 结果缺少稳定的执行过程、召回内容和版本证据，难以逐题复盘。

### 3.2 新方案

当前受控路径大致如下：

```text
用户问题
  ↓
LLM 生成低权限 IntentCandidate
  ↓
本地 schema 校验、实体解析和置信度门控
  ↓
IntentPlanCompiler 根据 intent 映射到固定 QueryPlan
  ↓
按场景执行图查询、PDS 直达或受限向量检索
  ↓
硬约束前置过滤 / parent scope 限定
  ↓
Milvus 召回候选（推荐路径）
  ↓
按 parent_id 聚合、软偏好重排
  ↓
PDS 回补最终正文
  ↓
EvidenceBundle + ClaimPolicy 约束 LLM 生成
```

新方案的核心变化不是简单地“换了一个向量库”，而是把检索从模型自由发挥改造成了有契约、有边界、有证据的执行链路。

## 4. 低权限意图数据模型

### 4.1 IntentCandidate 是什么

LLM 不直接返回 Cypher、SQL、Milvus filter 或数据库 ID，而是填写一个受限的 `IntentCandidate` 数据模型。模型描述的是“用户想做什么”，不是“系统应该如何执行”。

典型字段包括：

```text
intent              用户任务类型
confidence          意图置信度
entity_mentions     用户提到的实体原话
slots.ingredients   食材候选
slots.cuisines      菜系
slots.methods       蒸、煮、炒、炸等方法
slots.tools         微波炉、电饭煲等设备
slots.preferences   清淡、少步骤、家常等偏好
slots.meal_context  早餐、午餐、晚餐
slots.servings      目标份量
slots.time_budget   时间预算
```

模型额外受到严格 schema 约束，不能携带：

```text
recipe_id、node_id、parent_id、chunk_id、build_id
cypher、sql、where、filter、top_k、template_id
```

### 4.2 “低权限”的含义

低权限表示 LLM 输出即使被采纳，也只能影响需求理解和候选槽位，不能直接获得数据库执行权。

执行权限由本地代码掌握：

```text
LLM：这是一个 RECIPE_STEP 问题，实体是宫保鸡丁，步骤是 2
本地程序：使用 recipe_step_anchor_v1 固定模板执行
```

这样可以避免：

- LLM 编造实体 ID；
- LLM 自由生成危险查询；
- LLM 绕过候选数量和范围限制；
- LLM 将不确定实体静默替换成相似实体；
- LLM 把普通正文误当成已验证关系证据。

### 4.3 意图模型解决的问题

相较于旧版自由路由，低权限意图模型提供了：

- 统一输入结构：每类请求都具备可校验字段；
- 固定执行边界：模型不能把理解结果升级为查询权限；
- 可测试性：同一意图和槽位可重复编译为同一类 QueryPlan；
- 可审计性：可以记录模型候选、置信度、编译结果和终态原因；
- 安全降级：低置信度、歧义、实体不存在和依赖不可用可以在执行前终止。

## 5. 意图如何决定检索路线

路线不是由 LLM 自由输出的“我想查图谱”决定，而是由受限 `intent` 经过本地 `IntentPlanCompiler` 映射到固定模板。

### 5.1 单实体查询

典型问题：

```text
宫保鸡丁怎么做？
宫保鸡丁有哪些食材？
```

典型链路：

```text
实体解析
  ↓
确认是 Recipe
  ↓
PDS 取完整父文档
```

如果用户询问的是指定步骤：

```text
实体解析
  ↓
Neo4j 通过固定 recipe_step_anchor_v1 确认步骤关系
  ↓
根据 anchor/chunk 定位步骤
  ↓
PDS 返回对应步骤正文
```

这类精确查询通常不需要 Milvus。

### 5.2 实体关系查询

典型问题：

```text
鸡肉可以做哪些菜？
鸡肉可以和哪些蔬菜搭配？
腌肉技巧有哪些？
```

典型链路：

```text
实体解析
  ↓
Neo4j 固定关系/有限子图查询
  ↓
得到 Recipe、Ingredient 或 TechniqueChunk 节点
  ↓
根据 parent_id 或 anchor 去 PDS 回补证据
```

当前不是让 LLM 生成任意多跳 Cypher，而是使用白名单模板，例如：

```text
ingredient_recipes_v1
ingredient_vegetable_pairs_v1
technique_chunks_v1
recipe_step_anchor_v1
recipe_cuisine_filter_v1
```

### 5.3 推荐查询

典型问题：

```text
推荐几道带鸡蛋、清淡、20 分钟内的早餐。
我只有微波炉，推荐几道简单的菜。
```

推荐路线不要求“完全没有实体”。实体可以作为推荐条件：

```text
鸡蛋：用于缩小候选范围
清淡：软偏好
20 分钟内：硬约束
早餐：场景偏好
```

推荐路线通常为：

```text
意图识别
  ↓
实体解析和图谱范围查询
  ↓
PDS metadata 硬约束过滤
  ↓
Milvus 受限范围召回
  ↓
parent 级聚合与软偏好重排
  ↓
Top5 PDS 正文回补
```

### 5.4 严格营养和澄清路线

如果用户要求严格的营养数值、医疗适用性等，而当前没有经过治理的营养数据，系统进入终态：

```text
NUTRITION_EVIDENCE_INSUFFICIENT
```

低置信度、实体歧义、多任务或超出支持范围的请求进入：

```text
CLARIFY_OR_OUT_OF_SCOPE
```

## 6. 三类核心存储

### 6.1 Neo4j：实体和关系

Neo4j 负责回答：

> 实体是否存在？两个实体之间是否存在已验证关系？

典型节点：

```text
Recipe
Ingredient
CookingStep
TechniqueDoc
TechniqueChunk
```

典型关系：

```text
Recipe - REQUIRES -> Ingredient
Recipe - CONTAINS_STEP -> CookingStep
TechniqueDoc - HAS_CHUNK -> TechniqueChunk
```

例如“鸡蛋可以做什么菜”：

```text
Ingredient(鸡蛋)
  ← REQUIRES -
Recipe
```

例如“鸡蛋和番茄能做什么”：

```text
鸡蛋相关 Recipe 集合
  ∩
番茄相关 Recipe 集合
```

这属于固定模板的有限关系/子图查询，不是任意自由多跳查询。

### 6.2 PDS SQLite：父文档、元数据、chunk 和锚点

PDS 是版本化的 Parent Document Store，当前请求路径不会重新扫描 Markdown，也不会从 Milvus 反推正文。

核心表：

```text
builds
  build_id、来源指纹、构建版本、状态、计数

parents
  parent_id、node_type、title、full_content、metadata_json、content_hash

chunks
  chunk_id、parent_id、chunk_index、section_title、text、text_hash

anchors
  anchor_id、parent_id、chunk_id、ordinal、source_relation
```

PDS 的作用分为两类：

1. **正文回补**：根据 `parent_id` 取完整菜谱，或根据 anchor/chunk 取指定步骤/章节；
2. **轻量元数据过滤**：读取菜系、方法、设备、时长、份量等属性，计算硬约束范围。

PDS 过滤阶段只读取 `RecipeMetadata` 等轻量行，不会把所有菜谱正文全部读出再交给 Milvus。

### 6.3 Milvus：child chunk 向量召回

Milvus 保存拆分后的 child chunk 及其向量和关联信息，例如：

```text
chunk_id
parent_id
chunk_index
section_title
vector
build_id
text_hash
```

Milvus 负责：

```text
在已经限定的 parent_id 范围内，寻找和用户问题语义最相关的候选
```

Milvus 可以技术上支持 scalar metadata filter，但当前主路径把 PDS 作为硬约束和版本元数据的权威来源，再把已验证的 `parent_id` 范围传给 Milvus。这样可以避免 PDS 与 Milvus 保存两份可能不一致的菜谱属性。

## 7. 推荐链路中的硬约束和实体范围

推荐问题如果带有明确实体，实体不会被忽略。

例如：

```text
推荐带鸡蛋、番茄、清淡、20 分钟内的早餐。
```

处理顺序大致为：

### 7.1 解析并验证实体

```text
鸡蛋 → 唯一 Ingredient node_id
番茄 → 唯一 Ingredient node_id
```

如果实体不存在或存在歧义，直接终止或澄清，不自动用相似实体替换。

### 7.2 通过图关系得到实体范围

```text
鸡蛋相关 Recipe ID 集合
  ∩
番茄相关 Recipe ID 集合
```

这一步得到候选 `parent_id` 的基础范围。

### 7.3 在 PDS metadata 上执行其他硬约束

例如：

```text
total_minutes <= 20
recipe_cooking_appliances 包含目标设备
recipe_methods 满足目标方法
cuisine_type 符合目标菜系
```

过滤后得到最终允许的 parent 范围：

```text
[parent_001, parent_008, parent_023, ...]
```

### 7.4 把范围传给 Milvus

Milvus 不进行全库搜索，而是在这个 parent 范围内做向量检索：

```text
parent_id in [parent_001, parent_008, parent_023, ...]
```

因此硬约束不会被向量相似度突破。

## 8. Top30、chunk 聚合和 Top5 重排

### 8.1 Top30 的含义

Milvus 原始结果是多个 chunk 命中，但系统会先按 `parent_id` 聚合。因此推荐链路中的 Top30 指的是：

```text
Top30 个菜谱 parent 候选
```

不是 Top30 个独立 chunk。

原始命中可能是：

```text
chunk_1 → recipe_A
chunk_2 → recipe_A
chunk_3 → recipe_B
chunk_4 → recipe_C
```

聚合后是：

```text
recipe_A：包含 chunk_1、chunk_2
recipe_B：包含 chunk_3
recipe_C：包含 chunk_4
```

### 8.2 菜谱检索分数

当前 `CandidateMetadata` 的基础 `retrieval_score` 不是所有 chunk 分数的平均值，而是：

```text
retrieval_score = 最高 chunk 分数
                 + 章节覆盖奖励
                 + 相邻 chunk 覆盖奖励
```

也就是优先使用该菜谱最匹配的 chunk，同时用很小的奖励反映：

- 是否命中了多个章节；
- 是否命中了相邻的上下文 chunk；
- 证据覆盖是否更完整。

同一个菜谱下的 chunk 会去重后再参与聚合，不会让同一菜谱因为 chunk 数量多而重复占据多个最终名额。

### 8.3 软偏好重排

重排器对 parent 级候选计算最终分数：

```text
最终分数 = 归一化向量检索分
         + 软偏好调整
```

当前已实现的典型调整包括：

```text
清淡偏好：蒸、煮加分；油炸扣分
少步骤偏好：步骤少加分；耗时短加分；耗时过长扣分
份量偏好：份量完全匹配加分，接近目标小幅加分
```

流程为：

```text
Milvus chunk 命中
  ↓
按 parent_id 聚合
  ↓
得到 Top30 菜谱候选
  ↓
parent 级重排
  ↓
取 Top5 个不同 parent_id
  ↓
PDS 回补 Top5 完整正文
```

因此最终不会出现：

```text
Top5 全部来自同一篇菜谱的不同 chunk
```

## 9. 非推荐路线中的硬约束和软偏好

### 9.1 硬约束

硬约束会进入实际查询或范围计算，而不是只交给 LLM 最后判断。

例如：

```text
只能用微波炉
20 分钟内
不要油炸
必须是川菜
```

可能的执行位置包括：

- 图查询模板中的固定类型、关系或类别条件；
- PDS metadata 的本地范围过滤；
- Milvus 的 `parent_id` 范围过滤。

当前并不是所有硬约束都写进 Neo4j。实体关系由 Neo4j 确认，设备、时长、做法等菜谱属性主要由 PDS metadata 过滤。

### 9.2 软偏好

软偏好主要服务于“存在多个候选、需要排序”的推荐场景：

```text
清淡一点
最好少步骤
优先晚餐
适合两个人
```

如果用户问的是确定事实，例如：

```text
宫保鸡丁第 2 步是什么？
```

软偏好不应该让 LLM 从事实证据中随意挑选或改写步骤，而应直接返回已验证的第 2 步。

如果问题中同时出现实体条件和偏好排序，例如：

```text
鸡肉可以做哪些菜，优先推荐清淡的？
```

它已经接近推荐问题，应进入范围限定、召回和重排链路。

## 10. 安全降级和不伪造证据

新路径采用 fail-closed 原则：不能证明，就不继续猜。

### 10.1 实体不存在

```text
ENTITY_NOT_FOUND
```

不把相似实体当成用户输入的实体。

### 10.2 实体有歧义

```text
ENTITY_AMBIGUOUS
```

要求澄清，不静默选择其中一个。

### 10.3 图关系不存在

```text
GRAPH_RELATION_NOT_FOUND
```

不能用普通正文证据冒充图关系。

### 10.4 图服务不可用

```text
GRAPH_UNAVAILABLE
```

新规划路径不自动扩大到不受限的向量搜索。

### 10.5 硬约束没有结果

```text
NO_PREFERENCE_RESULTS
```

明确说明没有找到同时满足条件的菜谱。

### 10.6 向量或工件不可用

```text
VECTOR_UNAVAILABLE
ARTIFACT_MISMATCH
```

不使用版本不一致的向量结果继续生成答案。

### 10.7 严格营养证据不足

```text
NUTRITION_EVIDENCE_INSUFFICIENT
```

没有治理过的营养数值时，不根据“少油”“清淡”等自然语言编造脂肪、热量或医疗结论。

## 11. 最终全链路示例

用户输入：

> “我有鸡蛋和番茄，想做清淡的早餐，20 分钟内完成，推荐 5 道。”

系统处理：

```text
1. LLM 生成低权限 IntentCandidate
   intent = PREFERENCE_RECOMMEND
   entities = 鸡蛋、番茄
   meal_context = 早餐
   preference = 清淡
   time_budget = 20 分钟

2. 本地校验候选模型和置信度

3. EntityResolver 解析鸡蛋、番茄

4. Neo4j 查询：
   鸡蛋相关 Recipe 集合
   番茄相关 Recipe 集合
   两个集合取交集

5. PDS metadata 执行硬约束：
   total_minutes <= 20
   满足可用设备和做法条件

6. 得到允许的 parent_id 范围

7. Milvus 在限定范围内召回 child chunk

8. 按 parent_id 聚合成菜谱候选

9. 计算最高 chunk 分数、覆盖奖励和检索分

10. 根据“清淡”“早餐”等软偏好重排

11. 取最终 Top5 个菜谱 parent

12. PDS 回补 Top5 完整正文

13. EvidenceBuilder 组织证据和限制

14. LLM 只能基于证据生成最终回答
```

## 12. 验收和可追溯性

项目已建立逐题审计和真实场景验收能力，包括：

- IntentCandidate、QueryPlan 和约束编译结果记录；
- 图查询状态、实体解析结果和关系证据记录；
- Milvus 候选 Top30、重排版本和最终 Top5 记录；
- PDS build_id、来源指纹、chunk/parent linkage 校验；
- 失败题冻结回归、超时续跑和断点结果；
- 300 题真实场景硬规则验收及独立回答质量评分。

最终硬规则验收重点验证：

```text
来源完整
题目覆盖完整
每题只有一个成功终态
回答非空
不存在非执行状态触发检索
```

回答质量评分与硬规则验收是两套指标：硬规则确认系统有没有越界或违反执行契约，回答质量评分确认用户最终得到的答案是否完整、可读和可行动。

## 13. 当前架构中最容易混淆的边界

### 13.1 有实体不代表一定走实体查询

```text
“鸡蛋能做什么菜？”
→ 实体关系查询

“推荐带鸡蛋、清淡、20 分钟内的菜。”
→ 推荐查询，鸡蛋作为候选范围条件
```

判断依据是用户要查询事实，还是要求系统进行筛选和排序。

### 13.2 推荐路线不代表完全没有实体

推荐问题可以同时包含：

```text
实体范围：鸡蛋、番茄
硬约束：20 分钟内、只能微波炉
软偏好：清淡、少步骤、早餐
```

实体先用于图谱范围查询，属性约束再由 PDS metadata 处理。

### 13.3 Milvus 不是正文权威来源

```text
Milvus：找到相关 child chunk 和 parent_id
PDS：根据 parent_id 返回完整、版本一致的正文
```

### 13.4 软偏好不是让 LLM 最后自由挑选

推荐场景中的软偏好由本地重排器显式加分、扣分；LLM 负责基于最终证据组织答案，不负责重新发明排序规则。

## 14. 适合对外讲解的简短版本

> 我把原先由 LLM 自由决定检索路线的 GraphRAG 方案，改造成了受限意图规划和证据驱动的检索链路。LLM 先把用户需求解析成低权限结构化数据，本地代码根据意图选择固定查询模板；明确实体先通过 Neo4j 确认关系，菜谱属性硬约束在版本化 PDS metadata 上过滤，Milvus 只在合法 parent 范围内做向量召回。召回的 child chunk 会按 parent_id 聚合成菜谱候选，结合清淡、时长、步骤数等软偏好重排出 Top5，再从 PDS 回补完整正文交给 LLM 生成。实体不存在、关系无法验证或证据不足时，系统会安全停止，而不是让模型猜测。>
