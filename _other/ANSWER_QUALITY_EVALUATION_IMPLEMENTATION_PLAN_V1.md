# 最终 300 题两层评测实施方案 V1.2

## 1. 当前执行范围（优先级最高）

本文件把研究方案落实为可执行步骤。本轮只交付两件事：

```text
既有 300 题硬规则考试结果（完整复制、哈希核验、只读引用）
+
300 题最终回答的单次 LLM 回答效果评分（0-100 分）
```

RAG 召回、候选排序、Recall、Precision、MRR、nDCG、Top30/Top5、gold 构建和相关性标注均**暂缓**。它们需要先冻结“每题应该召回什么”的 gold；当前未具备这个前置条件，不能用缺失资料伪造 RAG 分数。本轮只在最终包中写明暂缓原因，不读取或构建 RAG gold，不把 RAG 暂缓视为失败。

同样，本轮不做人工逐题评分、A/B 双评审、共识、仲裁、60/30 题校准、90 题稳定性集、重复运行或以 AI fixture 作为正式评分的强制门槛。每个正式题目只保留一次成功的 LLM 评分；网络、超时或 JSON 解析失败时，只能在尚未取得有效评分前做有限技术重试。

既有来源运行固定为：

```text
_other/考试/检索重构真实场景考试包/结果/
  2026-08-15-intent-planner-300-005/
```

本实施不重跑该 300 题考试、不调用线上检索、不重新生成最终回答、不修改原始 `passed/failed`。当前 300 题均为 `passed`，故 300 题都进入回答效果评分。

## 2. 结果怎样理解

两张成绩单并列，不能混成一个总分：

| 成绩单 | 回答的问题 | 本轮来源 |
| --- | --- | --- |
| 硬规则 | 系统有没有违反既定契约或安全要求 | 既有 300 题考试，只读引用。 |
| 回答效果 | 最终回复是否贴题、体现偏好、理由或边界说清、好读且能执行 | 新增的单次 LLM 结构化评分。 |

回答效果高分不能抵消硬错误；回答效果低分也不能倒推出“检索一定不好”。RAG 在本轮显示为“暂缓”，不参与结论计算。

## 3. 阶段、产物和关卡

| 阶段 | 要做什么 | 主要产物 | 进入下一步的条件 |
| --- | --- | --- | --- |
| P0 | 固定来源并核验原考试 | 来源清单、哈希报告 | 300 题和审计可一一定位。 |
| P1 | 生成评分所需的标准输入 | `evaluation-cases.jsonl` | 每题恰一行，回答和审计可追溯。 |
| P2 | 记录 RAG 暂缓范围 | `rag-deferred.md` | 未计算、未伪造任何 RAG 分。 |
| P3 | 实现并验证单次评分器 | 评分器、配置、聚焦测试 | 前 3 个正式题可取得合法评分。 |
| P4 | 运行全部 300 题评分 | `quality-scorecard.json`、checkpoint | 每题有一次有效评分或真实未验证错误。 |
| P5 | 自动核验结果 | 验收报告 | 输入、公式、状态和计数一致。 |
| P6 | 归档完整最终包 | `_other/最终300测试/运行结果/<运行编号>/` | 原硬规则副本、新结果、结论和总览可追溯。 |

## 4. P0：来源核验和只读快照

1. 递归枚举来源运行的所有常规文件，按相对路径记录大小和 SHA-256。
2. 核验 `new-results.jsonl` 恰有 300 个不重复题号，且题号均能映射至 `frozen_questions.json`。
3. 对每题定位原始状态、审计 ID、用户问题、最终回答和必要的最终证据/限制说明。无法可靠解析的字段必须记录为缺失，不能让 LLM 猜测。
4. 生成 `source-run.json`、`source-integrity-report.json` 与 `source-integrity-report.md`，并保证整个过程不向来源目录写入。

若来源物理缺失或 300 题无法一一映射，标记 `SOURCE_INTEGRITY_FAILED`，停止 P1-P5，仍进入 P6 生成失败归档。失败归档不能冒充完整原考试副本。

## 5. P1：标准化评分输入

生成每题一行的 `evaluation-cases.jsonl`。最低字段如下：

```json
{
  "case_id": "S06-A-01",
  "scenario_id": "S06",
  "difficulty_code": "A",
  "source_status": "passed",
  "user_question": "...",
  "final_answer": "...",
  "audit_id": "...",
  "final_evidence": [],
  "limitations": [],
  "source_locations": {},
  "field_status": {}
}
```

规则：保留回答、证据和限制的来源定位与哈希；每个题号恰一行；任何缺失字段有明确原因；不在这一步打分。P1 仅供硬规则引用和回答效果评分使用，不为 RAG 解析候选、排序或 gold。

## 6. P2：RAG 暂缓声明

在运行目录写入 `rag-deferred.md`，固定说明：

- 本轮只评价用户看到的最终回答，不评价检索过程；
- 缺少逐题冻结的相关性 gold，不能可靠计算 Recall、Precision、MRR 或 nDCG；
- 本轮不生成 `rag-scorecard.json`、不生成 `DERIVED_AI_GOLD_V1`、不把 `N/A` 或 `RAG_UNVERIFIED` 伪装为分数；
- 后续启动独立 RAG 专项前，必须先冻结 gold、候选范围和相关性口径。

完成这份说明即可进入 P3，RAG 不存在本轮验收门槛。

## 7. P3：单次 LLM 回答效果评分器

所有新框架必须建立在：

```text
_other/最终300测试/
  工具/answer_quality_evaluation/   # 可运行源码
  配置/                             # 无密钥的 rubric、schema、运行配置说明
  tests/                            # 框架聚焦测试
```

不得修改、继续使用或把新逻辑写入 `_other/考试/检索重构真实场景考试包/工具/three_layer_evaluation/`。该目录属于旧 RAG/A-B 评审设计，只作为历史阅读材料保留。所有正式运行的输入、checkpoint、日志和结果只能写入 `运行结果/<运行编号>/`。

### 7.1 每题如何评分

评审器只能读取该题的封闭材料：用户问题、最终回答、必要的最终证据摘要、限制说明、场景权重和 rubric。不得访问网络、数据库、其他题、完整候选池、原硬测试结论或提示材料中的指令。

每题仅调用一个 LLM 评审。成功的评分必须是合法 JSON，评分器随后自行复算 100 分总分：

```json
{
  "task_score": 1,
  "preference_score": null,
  "evidence_expression_score": 1,
  "boundary_expression_score": null,
  "readability_score": 1,
  "total_score_100": 0,
  "issue_tags": ["OFF_TOPIC"],
  "evidence_notes": [],
  "confidence": "high",
  "review_reason": "不超过 400 字的中文理由"
}
```

维度和权重：

| 题型 | 任务完成 | 偏好贴合 | 证据表达 | 边界表达 | 可读与可执行 | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| S01-S05 正常回答 | 40 | 不适用 | 25 | 不适用 | 35 | 100 |
| S06/S07 推荐 | 25 | 35 | 20 | 不适用 | 20 | 100 |
| S05C、S08-S10 拒答或降级 | 30 | 不适用 | 不适用 | 45 | 25 | 100 |

原始维度均为 1-5 分，单项折算为 `权重 x (原始分 - 1) / 4`。程序必须校验分数范围、适用维度、标签枚举、证据 ID 与权重公式；不接受 LLM 自报但无法复算的总分。

### 7.2 输入、重试和落盘

- 证据只保留支持评分所需的紧凑摘要，设置长度上限；不把完整审计正文或 Top30 塞入请求。
- 先以单并发顺序运行正式 300 题中的前 3 题。这 3 题计入正式结果，不是试点或额外样本。
- 三题均成功后，继续余下 297 题；并发默认保持 1，仅在前三题稳定成功后才能提高到最多 2。
- 每题请求前写入输入哈希和 `PENDING` checkpoint；每次尝试记录开始/结束时间、耗时、模型、HTTP 或异常类型和尝试次数；取得合法评分后立即落盘为 `SCORED`。
- 仅在没有获得合法评分时可进行有限技术重试（建议最多 2 次重试）。一旦 `SCORED`，不得再次调用 LLM 改分。
- 耗尽重试后写 `QUALITY_UNVERIFIED`，所有评分字段与总分为 `null`，同时保留真实原始错误。不得用 `--skip-ai` 或占位分数伪装成评分。
- 若前三题任一题未能成功，先检查输入体积、超时、并发和服务配置；正常工程问题修复后只重试该未完成题。若外部服务仍不可用，停止剩余 297 题，形成真实受限归档，不得继续生成虚假的 300 题结果。

### 7.3 聚焦验证

实现阶段至少验证：来源解析、100 分权重复算、JSON schema、`QUALITY_UNVERIFIED`、checkpoint/续跑、已成功题不会二次评分、前 3 题关卡、最终包引用与哈希复制。这里的测试是程序正确性检查，不是 A/B 或稳定性重复评分。

## 8. P4：正式 300 题运行

1. 创建新的运行目录，不在原始 300 题目录写入结果。
2. 执行 P0、P1、P2；来源通过后才执行 P3/P4。
3. 创建 `hard-scorecard-reference.json`，仅引用既有硬规则结论、题号和审计 ID。
4. 运行前 3 个正式题；三题成功后续跑其余 297 题。中断后只读取 checkpoint 并处理 `PENDING` 或未记录的题，不重打 `SCORED` 题。
5. 输出 `quality-scorecard.json`、`judge-input-manifest.json` 和运行日志。汇总必须按场景、难度、维度、问题标签和 `QUALITY_UNVERIFIED` 状态展示。

## 9. P5：自动验收和结论状态

| 检查项 | 通过条件 |
| --- | --- |
| 来源完整性 | 300 个唯一题号、来源哈希、审计定位一致。 |
| 原结果保护 | 原始来源无写入；硬规则引用与原考试一致。 |
| 输入完整性 | `evaluation-cases.jsonl` 恰 300 行，每题状态明确。 |
| 单次原则 | 每题至多一次 `SCORED` 结果；技术失败没有伪造评分。 |
| 评分正确性 | JSON、适用维度、标签、证据 ID 和 100 分公式均通过程序校验。 |
| 汇总正确性 | 有效题数、未验证题数、场景/难度分和问题标签可由逐题卡复算。 |
| RAG 边界 | 存在暂缓说明；不存在 RAG 分数、gold 或其通过门槛。 |

自动结论只能是以下之一：

- `READY_FOR_AUTO_BASELINE`：来源完整，300 题均有一次有效评分，所有结构和公式检查通过；
- `AUTO_BASELINE_WITH_LIMITATIONS`：来源完整、计算正确，但存在一个或多个 `QUALITY_UNVERIFIED`，已列出真实原因；
- `NOT_READY`：来源不完整、前三题关卡未通过、评分卡结构或公式无法验证，或结果存在伪造/重复评分风险。

RAG 暂缓本身不得导致 `NOT_READY`。无论何种结论，都不改变既有硬规则考试结论。

## 10. P6：最终包归档和验收

最终根目录固定为：

```text
_other/最终300测试/运行结果/<运行编号>/
  00-最终总览.md
  01-原始300硬规则考试/
  02-评测输入与硬指标/
  03-RAG指标/本期暂缓说明.md
  04-回答效果评分/
  05-自动验收与结论/
  final-conclusion.json
  package-manifest.json
```

正常路径必须完整复制既有 300 题硬规则考试至 `01-原始300硬规则考试/`，并将复制后所有常规文件的相对路径、大小和 SHA-256 与 P0 清单逐项比较。只有 608 个来源文件（或 P0 固定的实际来源文件数）全部一致，才能称为“完整副本”。

`00-最终总览.md` 只需让人快速看懂：原硬规则结论、回答效果有效/未验证题数、全体和场景分、最低场景、常见问题标签、RAG 暂缓原因、自动验收状态和原始受限记录的区别。第一次受限归档必须保留，不删除、不改写，也不能称为正式评分结果。

验收后只更新 `_other/最终300测试/README.md` 与 `运行结果/README.md` 追加最新包索引，不能覆盖历史记录。旧 `NOT_READY` 包只存放于 `历史受限归档/`，不能混入正式运行结果目录。

## 11. 完成定义

本轮完成必须同时满足：

1. 原 300 题硬规则考试已完整复制且哈希核验，且没有被重跑或改写；
2. RAG 暂缓说明存在，未产生伪造的 RAG 评分；
3. 300 题按“先 3、后 297”的顺序执行，每个成功题恰有一次 LLM 评分；
4. 未成功题明确为 `QUALITY_UNVERIFIED` 并保留真实技术错误，不影响原硬规则结果；
5. 最终包可在一个目录下查看输入、逐题结果、自动验收、结论和总览；
6. 最终结论只并列展示硬规则和回答效果，不把两者或 RAG 混成一个分数。
