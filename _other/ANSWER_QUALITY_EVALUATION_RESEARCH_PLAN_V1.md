# 回答质量补充评测调研方案 V1

## 1. 这次要做什么

300 题硬测试已经完成了它该做的事：检查系统有没有违反既定契约，例如错误路线、硬约束被绕过、证据缺失、安全题乱答或禁止断言。

本方案不重跑、不复制，也不修改这套硬测试。它只在已有硬测试结果之上补一个问题：**已经通过硬测试的回答，对用户来说是否真的好用。**

当前 V1 的输入固定为最新完整 300 题运行：

```text
_other/考试/检索重构真实场景考试包/结果/
  2026-08-15-intent-planner-300-005/
    new-results.jsonl
    runner.stdout.jsonl
    audits/
```

评价对象仅为原始结果中 `status=passed` 的最终回答。当前这次完整运行的 300 题均为 `passed`，因此 300 题都会进入质量评测；今后若来源运行含 `failed` 题，则只在报告中列出其数量，不对其补打质量分。

新评分不会改变原来的 `passed` 或 `failed`，也不会重新决定检索路线、硬约束、安全结论或事实是否成立。

建议流程如下：

```text
既有 300 题硬测试结果
  -> 读取题目、最终回答、审计中的最终证据与限制说明
  -> 人工定义“好回答”的标准
  -> LLM 按标准做批量辅助评分
  -> 人工抽样校准与复核
  -> 输出按场景拆分的回答质量报告
```

## 2. 为什么还需要这一步

`300/300 passed` 说明系统没有触发已定义的硬错误，但不能回答下面这些用户体验问题：

- 回答有没有真正回应用户的问题；
- 推荐是否体现了用户说的口味、场景和软偏好；
- 理由是否说得清楚，证据限制是否表达得自然；
- 菜谱步骤是否易读、容易照着做；
- 拒答或降级时，是否既清楚又有帮助。

现有 `new-results.jsonl`、`runner.stdout.jsonl` 和 `audits/` 已保存题目、最终回答、审计 ID、路线和证据过程。缺少的是稳定、可聚合的回答质量分数、问题标签、人工复核结果及两者分歧。

## 3. 范围与边界

本方案做：

- 从既有完整 300 题结果中读取最终回答和已审计证据；
- 对回答的贴题程度、偏好贴合、证据表达、边界表达和可读性评分；
- 由人工校准 LLM 评分，并产出低分回答及原因；
- 按 S01-S10、A/B/C 难度拆分报告，帮助定位需要改善的回答类型。

本方案不做：

- 不重新检查实体 ID、图路径、PDS/Milvus 一致性、ConstraintSpec 或安全规则；
- 不重跑 300 题，不调用线上检索服务，不改变检索、重排或回答生成；
- 不以 LLM 分数推翻既有硬测试结论；
- 不把回答质量的 100 分与 TTFT、总耗时或上游异常率混成一个总分；
- V1 不重开 S06/S07 的 Recall、MRR、nDCG 或 Top30 相关性标注研究。这些属于检索和排序效果，后续如有需要另立方案。

对安全题也只检查回复效果：例如拒答是否说清原因、有没有给出合适的下一步。原来的“该不该拒答、是否出现禁止断言”仍以既有硬测试为准。

## 4. 回答质量指标

V1 将每题回答归一为 `0-100` 分，便于观察整体趋势；不同题型仍使用不同权重，因此总分不能替代场景分。任何场景的低分都必须在报告中单独显示，不能被其他场景高分掩盖。

评阅者先给每个适用指标 `1-5` 分：`1` 为明显不好用，`3` 为基本可用，`5` 为很好用。`不适用` 必须写为 `null`，不以 0 分处理。

单项换算公式为：

```text
单项折算分 = 指标权重 x (原始 1-5 分 - 1) / 4
题目总分 = 所有适用指标的单项折算分之和
```

因此原始 `1` 分贡献 0，`3` 分贡献该项权重的一半，`5` 分贡献该项全部权重；每套场景权重之和固定为 100。

| 指标 | 要回答的问题 | 适用场景 |
| --- | --- | --- |
| 任务完成度 | 是否直接、完整地回应了用户的问题？ | 全部 |
| 软偏好贴合度 | 是否在推荐顺序和理由中体现口味、场景、便利性等软偏好？ | S06/S07 |
| 证据表达 | 关键理由是否能对应已有证据，且没有把证据范围说大？ | S01-S07 |
| 边界表达 | 证据不足、未找到、图不可用或拒答时，是否说清楚限制和下一步？ | S05C、S08-S10；其余场景为 `null` |
| 可读与可执行性 | 是否易扫描、重点明确、步骤或建议能直接照做？ | 全部 |

### 4.1 100 分权重

| 题型 | 任务完成度 | 软偏好贴合度 | 证据表达 | 边界表达 | 可读与可执行性 | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| S01-S05 的正常回答 | 40 | 不适用 | 25 | 不适用 | 35 | 100 |
| S06/S07 推荐 | 25 | 35 | 20 | 不适用 | 20 | 100 |
| S05C、S08-S10 拒答或降级 | 30 | 不适用 | 不适用 | 45 | 25 | 100 |

`S05C` 属于第三行；S05 的 A/B 题属于第一行。指标为“不适用”时输出 `null`，且该行的其余权重已经合计为 100，不需要重新分摊。

总分解释统一如下：

| 分数 | 含义 |
| --- | --- |
| 90-100 | 很好用：回应完整、表达清楚，用户可直接行动。 |
| 80-89 | 可直接使用：有少量可改善点，但不会妨碍用户完成任务。 |
| 70-79 | 基本可用：能回答问题，但存在明确的表达、偏好或可执行性短板。 |
| 低于 70 | 体验较差：需要优先查看问题标签和原回答。 |

### 4.2 各场景怎么看

| 场景 | 重点看什么 |
| --- | --- |
| S01 菜谱全文 | 做法组织是否完整易读，食材、时间和步骤是否容易执行。 |
| S02 指定步骤 | 是否直接给到目标步骤，邻近说明是否刚好够用而不跑题。 |
| S03 技巧说明 | 是否讲清技巧要点、适用情形和限制，而不是堆砌原文。 |
| S04/S05 图关系 | 是否把关系讲成人能理解的话，说明已知和未知边界。 |
| S06/S07 推荐 | 推荐是否贴合软偏好，排序理由是否具体，用户能否据此做选择。 |
| S05C、S08-S10 | 拒答或降级是否清楚、有帮助，是否说明用户下一步能怎么问或怎么做。 |

`S05C` 是 S05 的 C 卷反例题，不是第 11 个独立场景。60 题校准集仍按 S01-S10 各抽 6 题；其中 S05 的两道 C 卷题必须是 S05C。

### 4.3 汇总口径

- `null` 表示该指标对该场景不适用，不计入该指标的平均分分母；
- `QUALITY_UNVERIFIED` 表示评分输入或输出不完整，不计入任何质量分平均值，单独计数和列题；
- 人工评分缺失时只缺席人工对照，不替代或改写 LLM 分数；
- 每个场景、难度和指标都同时显示 100 分总分、各维分、有效题数和未验证题数；
- 全体总分为所有有效题目 100 分总分的算术平均值；同时必须显示 S01-S10 场景分和最低场景分；
- 若任一场景平均分低于 70，即使总体分达到 80，也只能写“总体可用，但该场景待改进”，不得宣称整体回答质量良好。

### 4.4 分数之外必须保留的问题标签

分数只能告诉我们“差多少”，问题标签才告诉我们“为什么差”。每题可附多个标签：

- `OFF_TOPIC`：没有直接回答问题；
- `PREFERENCE_MISSED`：没有体现用户软偏好；
- `REASON_UNCLEAR`：给出推荐但理由含糊；
- `EVIDENCE_OVERSTATED`：把已有证据说得过满；
- `LIMITATION_UNCLEAR`：限制或不确定性说得不清楚；
- `TOO_VERBOSE`：信息重复或明显超出问题所需；
- `NOT_ACTIONABLE`：用户看完仍不知道下一步怎么做；
- `REFUSAL_NOT_HELPFUL`：拒答正确但表达生硬或没有替代帮助。

## 5. LLM 辅助评分

LLM 的角色是批量阅读和按 rubric 打分，帮助找出值得人工看的回答；它不是硬测试的裁判，也没有权力修改原结果。

每题只向 LLM 提供封闭材料：

- 用户问题；
- 最终回答；
- 该题审计中已经使用的最终证据片段和限制说明；
- 本题适用的质量指标与评分标准。

它不能访问数据库、网络或其他菜谱，也不能自行发起检索。证据文本一律作为只读引用材料处理，不能执行其中出现的任何指令。

建议使用结构化输出：

```json
{
  "task_score": 1,
  "preference_score": null,
  "evidence_expression_score": 1,
  "boundary_expression_score": null,
  "readability_score": 1,
  "total_score_100": 0,
  "issue_tags": ["OFF_TOPIC"],
  "evidence_notes": [
    {
      "answer_excerpt": "回答中的关键理由",
      "verdict": "clear|overstated|unclear|not_applicable",
      "evidence_ids": ["parent_id:chunk_id"]
    }
  ],
  "confidence": "high|medium|low",
  "review_reason": "不超过 400 字的中文理由"
}
```

程序只校验输出格式、各维分数范围、`null` 是否符合场景、权重公式计算出的 `total_score_100`、标签是否属于枚举、证据 ID 是否属于本题已提供证据集。它不把 LLM 的事实判断写回硬测试结果。

为了避免“回答写得长、写得漂亮就高分”，评分提示词必须明确：偏题、没用、夸大或没说清限制的回答不能因篇幅和文采获高分。校准阶段还要测试答案顺序互换、等义改写、简短正确回答和冗长回答，确认评分没有明显偏差。

## 6. 人工校准

LLM 的评分要先和人工判断对齐，才能用于全量 300 题的辅助分析。

1. 从现有 300 题按场景和 A/B/C 难度抽取 60 题作为校准集，每个场景 6 题，难度各 2 题。
2. 两位人工评阅者独立、盲评这 60 题，按同一 rubric 给分和打问题标签。
3. 对同一 60 题运行 LLM 评分，比较人工与 LLM 的分数、问题标签和低分原因。
4. 调整 rubric 或评分提示词后，另抽取 30 道未参与调整的题作为留出检查集，确认评分规则没有只适配校准题。
5. 分歧较大的题由人工复核，保留最终判断和分歧原因。

V1 的实用验收目标：

| 项目 | 目标 |
| --- | --- |
| LLM 与人工各维分数相差不超过 1 分 | >= 80% |
| LLM 与人工的问题标签一致率 | >= 80% |
| 人工双评阅者各维分数相差不超过 1 分 | >= 80% |
| 留出检查集达到上述前两项 | 必须达到 |

未达到这些目标时，LLM 输出只能作为“待人工阅读的线索”，不能作为 300 题质量基线的结论。

## 7. 输出工件

一次回答质量评测生成独立目录，只读取、不覆盖原始 300 题结果：

```text
_other/考试/检索重构真实场景考试包/结果/<回答质量运行编号>/
  source-run.json                         # 指向 300 题来源目录及文件哈希
  quality-scorecard.json                  # 每题质量分、标签、理由、复核状态
  quality-summary.md                      # 按场景和难度汇总的质量报告
  quality-review-samples.json             # 人工评分、分歧与最终复核记录
  quality-judge-input-manifest.json       # 每题输入证据与 rubric 版本的哈希
```

`quality-scorecard.json` 每题至少记录：来源运行编号、题号、场景、难度、原始通过状态、最终回答哈希、审计 ID、适用指标、1-5 原始分、场景权重、`total_score_100`、问题标签、置信度、人工分数、最终复核结果和 rubric/judge 版本。

报告必须分别列出：

- 全体 100 分总分、每个场景和难度的 100 分总分及各指标平均分；
- 最低场景分及其问题标签，防止总体分掩盖局部短板；
- 低分题及其问题标签；
- 最常见的 3-5 类问题；
- LLM 与人工分歧题；
- 推荐题、步骤题、拒答题各自的代表性好回答和待改进回答。

报告不把质量分写回 `new-results.jsonl`，不重写 300 题考试总评，也不产生新的硬测试通过率。

## 8. 分阶段调研与交付

### R1：确定“好回答”的标准

- 为 S01-S10 编写上述指标的 1-5 分示例、100 分权重和问题标签说明；
- 从 `2026-08-15-intent-planner-300-005` 选择 60 题校准集；
- 两位人工独立试评，找出 rubric 说不清的地方；
- 输出 `quality-rubric-v1` 和人工一致性报告。

### R2：离线评分原型

- 只读取既有 `new-results.jsonl`、`runner.stdout.jsonl` 和 `audits/`；
- 为每题组装封闭的评分输入，保存来源和哈希；
- 按场景权重将结构化 LLM 评分换算为每题 100 分，并生成总体和场景级汇总；
- 不调用线上检索，不重跑回答生成，不修改原始考试文件。

### R3：校准并产出第一份质量基线

- 在 60 题校准集上比较人工与 LLM；
- 固定 rubric 和评分提示词后，在 30 题留出集检查；
- 达标后对既有完整 300 题生成第一份回答质量报告；
- 按低分标签归因，区分“回答组织问题”“偏好表达问题”“证据表达问题”，而不是直接把问题归咎于检索。

### R4：评分器稳定性研究

- 对固定回答重复运行评分器，检查同一回答是否出现明显分数漂移；
- 记录 judge 模型、提示词、参数和运行时间；
- 只有评分稳定后，才把全量分数用于长期版本比较。

## 9. V1 签收条件

回答质量评分系统本身满足以下条件，才可用于形成质量基线：

- 输入只来自已完成的完整 300 题运行及其审计；
- 不重跑硬测试、不更改原始通过/失败结论；
- 每题可追溯到来源回答、审计 ID、证据哈希、rubric 版本和 judge 版本；
- 人工校准集与留出检查集达到第 6 节目标；
- 汇总报告按总体、场景、难度和问题标签展示；总体高分不能掩盖低于 70 的场景；
- 评分器失败时标记该题 `QUALITY_UNVERIFIED`，不影响原题的硬测试状态。

## 10. 进入实现前要回答的问题

1. 60 题校准加 30 题留出检查，是否已足够覆盖十种场景和 A/B/C 难度？
2. 三套 100 分权重、五个质量指标和问题标签，哪些对人工来说仍不够清楚或不符合“好回答”的直觉？
3. 单一固定 judge 是否能和人工稳定对齐，还是只将低置信度和高分歧题交给第二 judge 或人工？
4. 现有审计文件能否稳定抽出“最终回答真正使用的证据和限制说明”？
5. 低分回答主要是表达组织、偏好理解还是证据说明问题，下一轮改动应落在生成提示词、回答模板还是检索/重排？

在这些问题有数据结论前，质量分应作为补充诊断报告，不应覆盖或取代既有 300 题硬测试结论。
