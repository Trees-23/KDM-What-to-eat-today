# 回答质量评测调研方案 V1

## 1. 结论先行

当前 300 题运行器回答的是“系统是否违反已定义的硬契约”，而不是“回答质量是否足够好”。
`300/300 passed` 可以作为签收门禁通过的证据，但不能直接换算成用户体验质量分。

建议建立两层评测：

```text
程序硬规则门禁
  -> 未通过：本轮不可签收
  -> 通过：进入回答质量评分
      -> 程序核验可验证事实
      -> LLM 评阅回答质量
      -> 人工抽检校准 LLM
      -> 输出按场景拆分的成绩单
```

LLM 只能充当受限的“语言与证据评阅员”，不能成为硬规则、数据事实或发布决策的最终裁判。

## 2. 已有基础与缺口

### 2.1 已有能力

`_other/考试/检索重构真实场景考试包/场景与评分标准.md` 已定义了检索、证据、安全和延迟指标：Recall、MRR、nDCG、路由准确率、证据完整率、证据链接率、回答忠实度、TTFT、总耗时和 P95。

当前 planner 启用态 300 题运行器已经能检查：

- 题目覆盖、审计文件、PDS/Milvus 联合工件一致性；
- 正确路线、必需图事实或 PDS 正文、空回答；
- S06/S07 的 ConstraintSpec、硬范围、Top30 metadata、Top5 回补和固定重排版本；
- S05C、S08、S09、S10 的安全收敛；
- 禁止的严格营养表达和无依据关系表达的部分契约。

### 2.2 当前缺口

当前 `new-results.jsonl` 的结构主要保留通过/失败、审计 ID、耗时和路线摘要。它没有为每题稳定写入下列可聚合质量字段：

- 冻结后的分级相关性 gold 与最终排序列表；
- 回答中的关键结论与证据片段的逐条对应；
- 回答是否真正满足软偏好、是否易读可执行；
- 主生成成功、确定性降级、上游异常三者的独立统计；
- LLM 评阅结果、人类复核结果和两者分歧。

仓库现有 `工具/汇总结果.py` 支持旧式 `ranking/gold_items/checks/timing` 成绩单，但不能把目前的 planner 运行器结果直接当成完整质量评测输入。直接给当前 300/300 贴一个总分会伪造尚未采集的指标。

## 3. 范围与非目标

本方案评估用户可见回答质量，以及它是否忠实使用已产生的证据。它不改变检索、PDS、重排或回答生成行为。

本方案不做：

- 用 LLM 判定实体 ID、图路径、设备/做法 metadata 或 PDS/Milvus 一致性；
- 用 LLM 放宽“不要油炸”“只能微波炉”等硬约束；
- 将模型的主观偏好当作菜谱事实；
- 以某几个固定菜名、题号或样本的特例替代通用评分规则；
- 用总分掩盖任何安全或硬约束失败。

## 4. 两层判定

### 4.1 第一层：不可补偿的门禁

任一项失败，本轮标记为 `NOT_SIGNABLE`，不计算“可发布”的质量等级：

| 门禁 | 程序判定依据 |
| --- | --- |
| 覆盖与审计 | 300 题完整、无重复、审计齐全、活动工件可验证 |
| 硬约束 | S06/S07 的 Top30 与最终 Top5 均满足 ConstraintSpec；空硬范围不回退全库 |
| 事实与证据 | 必需图事实、PDS parent/chunk/sourcePath 链接可验证 |
| 安全收敛 | S05C/S08/S09/S10 按题目契约拒答或降级，零关系幻觉 |
| 禁止断言 | 无低脂/低热量/医疗适用等未经治理证据的严格结论 |
| 工件完整性 | PDS、Milvus、联合 manifest 不一致时不可伪装为通过 |

这些项目不交给 LLM 判断。它们要么来自受控 metadata，要么来自审计事件，要么由确定性规则检查。

### 4.2 第二层：100 分回答质量成绩单

只有门禁通过的题目进入质量评分。题目级总分为 100 分：

| 维度 | 分值 | 评分问题 |
| --- | ---: | --- |
| 任务完成度 | 30 | 是否回答了用户真正问的事，是否给出足够的可执行信息？ |
| 偏好贴合度 | 25 | 对软偏好和风味/场景的理解是否体现在推荐顺序和理由中？ |
| 证据表达质量 | 25 | 每个关键理由是否准确地由最终证据支持，是否说清证据边界？ |
| 诚实与安全表达 | 10 | 是否避免夸大，证据不足时是否保留限制？ |
| 可读与可用性 | 10 | 是否易扫描、推荐明确、没有无关重复或难以执行的表述？ |

硬约束满足不在这 100 分中重复加分。它是通行证，不是奖励项；否则会出现“违反不要油炸，但语言写得好所以高分”的错误结论。

## 5. 不同场景的评分方式

不能把十类问题放进同一个“推荐好不好”的尺子中。

| 场景 | 质量重点 | 不适用项 |
| --- | --- | --- |
| S01 菜谱全文 | 菜谱对不对、正文是否完整、步骤是否可执行 | 软偏好贴合度 |
| S02 指定步骤 | 步骤号准确、邻近上下文足够、没有串步骤 | 菜谱排名质量 |
| S03 技巧说明 | 是否答到技巧重点、是否保留原文边界 | 菜谱推荐相关性 |
| S04/S05 图关系 | 关系解释是否清楚、图事实与正文是否衔接 | 纯向量相关性 |
| S06/S07 推荐 | 偏好贴合、排序理由、Top5 证据、限制表达 | 以单一标准答案作唯一判定 |
| S08/S09/S10 安全题 | 拒答是否清晰、有帮助、没有伪造事实 | Recall/MRR/nDCG |

最终报告必须给出：总体分、每个场景分、A/B/C 难度分和安全题独立通过率。不得只用一个平均数覆盖某个场景的明显退化。

## 6. LLM 评阅设计

### 6.1 LLM 可评的内容

LLM 只接收本题封闭材料：用户问题、最终回答、最终 Top5 PDS 正文或图事实、可见限制、允许声称的事实边界。它可以评价：

- 回答是否贴题、是否真正回应了用户；
- 对软偏好、口味、场景和表达需求的贴合程度；
- 关键理由是否由提供的正文或事实支持；
- 是否把不确定性、不可证明项说清楚；
- 结构、简洁性、可读性和行动建议。

### 6.2 LLM 禁止评的内容

LLM 不得自行浏览数据库、网络或全库菜谱；不得猜测未提供的证据；不得改写硬约束；不得生成实体 ID、QueryPlan、过滤条件、权重或新的检索请求。

设备、做法、时间、份量、食材关系和 artifact 一致性只接受程序提供的已验证事实。若 LLM 判断与程序硬核验冲突，程序结论优先，并将该题写入复核队列。

### 6.3 受限输出格式

评阅 LLM 必须以 JSON Schema 输出，禁止自由散文作为机器判定依据。建议字段：

```json
{
  "task_score": 0,
  "preference_score": 0,
  "evidence_score": 0,
  "honesty_score": 0,
  "clarity_score": 0,
  "key_claims": [
    {
      "claim": "回答中的关键结论",
      "verdict": "supported|partially_supported|unsupported|not_applicable",
      "evidence_ids": ["parent_id:chunk_id"]
    }
  ],
  "confidence": "high|medium|low",
  "review_reason": "不超过 400 字的中文理由"
}
```

程序必须验证：

- 分数范围和字段类型正确；
- `evidence_ids` 只属于本题最终证据集；
- 评分维度之和为 100；
- `unsupported` 的关键结论进入复核队列；
- 安全题使用对应的拒答质量 rubric，而不是强迫其推荐菜谱。

## 7. 人工校准与防止“LLM 自嗨”

LLM 评分不能只靠一次运行就成为真相。建议分三层进行：

1. 先从每个场景抽 6 题，共 60 题，A/B/C 各 2 题，由两位人工评阅者独立按同一 rubric 打分。
2. 其中至少 30 题与 LLM 评分对照。观察维度分数差、`supported/unsupported` 一致率和安全题判断一致率。
3. 对分差大于 15 分、LLM 低置信度、LLM 与程序冲突、或门禁临界的题目，进入人工复核，不以平均分掩盖分歧。

V1 的校准建议目标：

| 项目 | 目标 |
| --- | --- |
| LLM 与人工总分差不超过 10 分的比例 | >= 80% |
| 关键结论证据判断一致率 | >= 90% |
| 安全题“应拒答/应降级”一致率 | 100% |
| 人工双评阅者分差不超过 10 分的比例 | >= 80% |

未达到校准目标时，只能把 LLM 输出称为“研究性辅助评分”，不能用于发布结论。

## 8. 检索排名与推荐相关性

S01-S05 的排名题继续使用开考前冻结的 gold 和分级相关性标签，计算 Recall@1/3/5、Precision@1/3/5、MRR@5、nDCG@5 与 Hit Rate@1/3/5。

S06/S07 不能由 LLM 临场杜撰“唯一正确菜名”。建议流程：

1. 固定活动 PDS build、题库版本、ConstraintSpec、候选 Top30 和最终 Top5；
2. 对固定候选建立 `0/1/2/3` 分级相关性标注：不相关、弱相关、相关、强相关；
3. 标注只评价软偏好与用户任务目标，硬约束仍由程序先判；
4. 标注由人工完成，LLM 可提出初稿但必须人工确认；
5. 对冻结后的标签计算 nDCG@5、MRR@5 和偏好贴合度。

每当 PDS build、菜谱 metadata 治理版本、题干或约束规则变更时，相关性标签必须重新版本化；不能沿用不再对应当前候选集的旧 gold。

## 9. 性能与稳定性成绩

性能不应混进“回答写得好不好”，但必须和质量成绩一起展示。

建议记录并分开统计：

- TTFT P50/P95；
- 总耗时 P50/P95/P99 和最大值；
- 主生成成功率；
- 确定性降级成功率；
- 上游模型超时、断连、限流次数；
- 空回答率和重试次数；
- 同一题重复执行的分数方差与结果稳定性。

初始 SLO 建议采用绿黄红而非立即二元淘汰：

| 指标 | 绿色 | 黄色 | 红色 |
| --- | --- | --- | --- |
| P95 总耗时 | <= 30 秒 | 30-45 秒 | > 45 秒 |
| 主生成异常率 | <= 0.5% | 0.5%-2% | > 2% |
| 空回答率 | 0 | 0 | > 0 |
| 硬约束或安全失败 | 0 | 不适用 | > 0，直接不可签收 |

阈值在连续三次运行后再根据真实用户等待容忍度调整；不得为了让本次结果变绿而事后修改阈值。

## 10. 输出工件

一次质量评测应生成独立目录，不能覆盖原始考试记录：

```text
_other/考试/检索重构真实场景考试包/结果/<运行编号>/
  acceptance-report.json                 # 既有硬规则结果
  quality-scorecard.json                 # 可机器读取的题目级质量分
  quality-summary.md                     # 总分、场景分、SLO 与风险
  quality-review-samples.json            # 人工抽检与分歧处理记录
  quality-judge-input-manifest.json      # 每题输入证据的哈希，不存密钥
  audits/                                # 既有检索审计
```

`quality-scorecard.json` 每题至少记录：试卷和工件版本、题号、场景、门禁状态、程序事实检查、LLM 各维分数、总分、引用证据 ID、置信度、是否需要复核、人工最终分和耗时。

## 11. 分阶段调研与交付

### 阶段 R1：指标与样本标注研究

- 从现有 300 题抽取 60 题校准集；
- 编写每个场景的人工 rubric 和 `0/1/2/3` 推荐相关性标签说明；
- 两位评阅者完成独立标注，记录分歧；
- 确定安全题、推荐题、实体题各自的“不适用”规则。

产出：`quality-rubric-v1`、校准样本、标注一致性报告。

### 阶段 R2：离线评分原型

- 只读取既有运行结果和审计，不调用线上检索服务；
- 生成受限的 LLM judge 输入，校验其 JSON 与证据引用；
- 实现题目级成绩单和场景级汇总；
- 与人工 30 题对照，调整 rubric，不调整硬规则。

产出：可复跑的离线 `quality-scorecard` 原型和成本报告。

### 阶段 R3：评分器验收

- 为输入组装、Schema 校验、证据 ID 越权、分数边界、安全题 rubric、聚合计算编写单元测试；
- 对 60 题校准集运行，确认达到第 7 节的人工一致性目标；
- 对完整 300 题生成第一次质量基线；
- 单独比较每个场景与 A/B/C 难度，列出低分题和可复现原因。

产出：`quality-scorecard-v1` 基线报告。

### 阶段 R4：稳定性研究

- 对固定 30 题进行至少三轮重复执行；
- 比较评分方差、重排稳定性、主生成异常与降级结果；
- 再决定性能 SLO 是否需要收紧或放宽。

产出：稳定性报告和正式发布阈值建议。

## 12. V1 签收条件

质量评分系统本身要满足以下条件，才可作为发布依据：

- 评分输入完全来自冻结题目、最终回答和已审计最终证据；
- LLM 无法访问数据库、网络或额外检索能力；
- 所有硬规则仍由程序判定，且失败不可被质量分抵消；
- 每题能追溯到 rubric 版本、judge prompt 版本、证据哈希和审计 ID；
- 人工校准达到第 7 节目标；
- 汇总报告分开列出门禁、质量、性能、成本与待复核题；
- 评分器失败时只标记该题 `QUALITY_UNVERIFIED`，不得修改原始考试通过/失败结论。

## 13. 研究问题

在进入实现前，需要以校准样本回答这些问题：

1. 60 题人工样本是否足以覆盖各场景的表达差异，还是需要扩展到 90 题？
2. 单一固定 judge 是否已达到与人工足够一致，还是仅对低置信度题启用第二 judge？
3. 推荐题的软偏好相关性标签能否稳定复用，PDS build 变化后重标成本是多少？
4. 哪些回答质量低分真正来自检索排序，哪些来自生成表达，避免把生成问题误修到召回层？
5. 当前 P95 耗时和主生成异常率是否符合实际产品容忍度？

上述问题有数据结论前，不应把质量评分总分用于合并或发布决策。
