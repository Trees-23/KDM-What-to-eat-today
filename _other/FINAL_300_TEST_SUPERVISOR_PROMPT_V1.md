## 一、分支就绪关卡（先完成，才可开始测试）

本次测试必须从最新的 `origin/main` 单独开分支执行，不能沿用本提示词所在的文档分支，也不能在 `main` 上直接执行。以下步骤是 P0 之前的强制关卡：

```bash
git fetch origin --prune
git switch -c codex/final-300-evaluation origin/main
git push -u origin codex/final-300-evaluation
```

执行时必须遵守以下规则：

- 先检查 `git status --short`、当前分支和 `origin/main`；不得以本地旧 `main` 代替 `origin/main`；
- 若 `codex/final-300-evaluation` 已存在，则新建一个唯一、ASCII 的替代名，例如 `codex/final-300-evaluation-20260815`，并在最终报告中写明实际分支名；
- 新分支的起点必须等于开始时的 `origin/main` 提交。记录 `git rev-parse HEAD` 与 `git rev-parse origin/main`，并用 `test "$(git rev-parse HEAD)" = "$(git rev-parse origin/main)"` 验证二者完全相等；
- 分支创建后立即推送，并创建或维护一个以 `main` 为基线的草稿 PR；该 PR 用于持续保存本次测试的代码、脚本、结果清单和文档；
- 不得在 `main`、本提示词的维护分支或用户既有分支运行 P0-P6、写入最终包或提交测试产物；
- 若受保护的本地改动使切换/建分支不安全，不能 stash、reset、clean、覆盖改动或用 worktree 绕过。应在最终交付中如实报告 `NOT_READY` 及阻塞原因，不能在错误分支上继续；
- 未获得用户明确合并授权前，测试分支的 PR 不得合并 `main`。

只有上述关卡通过后，才开始读取后续材料和执行 P0。最终包的 `05-自动验收与结论/` 中必须保留 `branch-baseline.json`，记录实际分支、`origin/main` 起点 SHA、创建时间、PR 链接和这项关卡的校验结果。

## 五、持续推进规则

你必须按 P0 -> P6 顺序推进。每阶段都要执行该阶段的进入条件、实现、测试和退出条件；不要只把文档改好就宣布完成。

### 正常问题：自行处理后继续

以下问题属于你的执行责任，不应暂停等待用户：

- JSON/JSONL/Markdown 字段解析失败：检查真实样本，修解析器，补 fixture 和测试，再重跑该阶段；
- 旧汇总器与本次 `new-results.jsonl + passed` 格式不兼容：实现新标准化读取层，不强套旧脚本；
- RAG gold、候选、Top30/Top5 或审计字段缺失：按实施方案写 `N/A` 或 `RAG_UNVERIFIED`，保留原因并继续完成其他可算项；
- 找不到历史冻结的 S06/S07 分级 gold：执行 `DERIVED_AI_GOLD_V1` 自动相关性流程，明确 `TOP30_ONLY`，绝不冒充全库 Recall；
- AI 输出不是合法 JSON、证据 ID 越界、A/B 分歧或单次调用失败：用结构校验、重试、仲裁和 `QUALITY_UNVERIFIED` 规则处理；
- 测试失败：定位根因，修复代码或配置，补回归测试，然后重新验证；
- 最终归档复制不完整或哈希不一致：重新复制到新的或清理后的本任务目标目录，重做哈希比对，不能跳过。

### 真正外部阻塞：仍要完成可完成部分

只有以下情况可以不产生完整自动基线：AI 服务凭据/权限不可用、所有可用模型服务失效、来源文件物理丢失且仓库内找不到副本、或系统权限禁止必要操作。

即使发生上述阻塞，你也必须：

1. 尝试安全的本地替代和已有配置，不泄露任何密钥；
2. 完成所有不依赖该阻塞项的阶段；
3. 在最终归档中生成 `NOT_READY` 结论、精确阻塞原因、已完成清单和可从何处继续的命令；
4. 若来源完整，复制并核验既有硬规则考试；若来源物理缺失，只复制仍可读取的文件，生成 `source-missing-manifest.json`，并在总览第一行标明“未生成完整副本”；
5. 只在最终交付时向用户说明阻塞，不把半成品伪装为完成。

不要因为一个非关键题或一个可标记的未验证指标停止整个流程。使用状态、证据和范围表达真实限制，然后继续。

## 六、必须实际完成的阶段

### P0/P1：来源核验与标准化

- 先运行 P0；若得到 `SOURCE_INTEGRITY_FAILED`，不要运行本节其余 P1 动作，直接按 P6 异常归档规则收尾；
- 校验 300 个唯一题号、来源哈希、审计定位和最终回答；
- 创建新的标准化输入层，不直接改写原结果；
- 每题每个字段明确 `PRESENT`、`NOT_APPLICABLE` 或 `MISSING`；
- 来源或审计缺失必须列出题号，不允许静默跳过。

### P2：RAG gold 和适用范围

- 先判安全题和正确空范围的 `N/A`，再检查可计算性；
- 优先使用可追溯的历史冻结 gold；
- S06/S07 缺历史分级 gold 时，执行双 AI 独立相关性、规则硬约束、仲裁和版本化 `DERIVED_AI_GOLD_V1`；
- 对 `TOP30_ONLY` 派生 gold，只计算 Top30 候选池内的选择/排序指标，绝不计算或写成全库 Recall；
- 校验 `candidate_top30` 和 `final_top5` 的顺序、唯一性、Top5 是 Top30 子集；失败就写 `RAG_UNVERIFIED`。

### P3：实现与测试

- 实现实施方案列出的标准化、gold、RAG、硬指标引用、回答效果、验收和渲染组件；
- 每个指标公式、状态转换、Top30/Top5 规则、分数权重和最终归档都要有可重复的自动化测试；
- 加入回答效果反偏差 fixtures：偏题冗长、简短完整、证据顺序置换、证据注入指令、拒答边界不清；
- 先跑聚焦测试，再跑与改动范围相符的完整测试；失败时修复并重跑。

### P4/P5：正式运行与自动验收

- 生成三张独立评分卡；
- 回答效果用结构校验、AI A、AI B、共识、仲裁、公式复算完成，不需要人工打分；
- 固定 90 题稳定性集，重复运行 3 次，按实施方案阈值验收；
- 所有结果必须有数值、`N/A`、`RAG_UNVERIFIED` 或 `QUALITY_UNVERIFIED`，不能出现无解释的空值；
- 输出 `READY_FOR_AUTO_BASELINE`、`AUTO_BASELINE_WITH_LIMITATIONS` 或 `NOT_READY` 之一，且理由可追溯。

### P6：最终 300 测试归档

必须按实施方案的目录结构写入：

```text
_other/最终300测试/<最终测试运行编号>/
  00-最终总览.md
  01-原始300硬规则考试/
    source-run.json
    source-copy-manifest.json
    2026-08-15-intent-planner-300-005/    # 来源完整副本，含 audits/
  02-三层评测输入与硬指标/
  03-RAG指标/
  04-回答效果/
  05-自动验收与结论/
```

归档前后都要递归比较来源目录全部常规文件的相对路径、大小和 SHA-256。正常路径中，原硬规则考试完整副本、三层结果、自动验收、最终结论、总览和最终包清单缺任何一个，不能称为完成。若来源物理缺失，只能生成带 `source-missing-manifest.json` 的 `NOT_READY` 失败归档，绝不称为“完整副本”。更新 `_other/最终300测试/README.md` 时只能追加新的最终包记录，不能覆盖历史记录。
