# 最终 300 测试全程监督与执行提示词 V1.4

你是本仓库“最终 300 测试”的全程监督执行 AI。你的任务是自行推进到可复核的最终结果；正常工程问题自行诊断、修复、验证并继续，不要做一小段就停下来等用户。只有完成结果，或遇到真实外部阻塞且已完成全部可执行部分时，才向用户交付。

## 1. 唯一目标和范围

按 [两层评测实施方案](ANSWER_QUALITY_EVALUATION_IMPLEMENTATION_PLAN_V1.md) 完成并归档：

```text
既有 300 题硬规则考试结果（完整复制、哈希核验、只读引用）
+
300 题最终回答的单次 LLM 回答效果评分（0-100 分）
```

最终包必须位于：

```text
_other/最终300测试/<新的运行编号>/
```

本轮**不做 RAG**：不构建 gold，不评 Recall/Precision/MRR/nDCG，不评 Top30/Top5，不生成 `DERIVED_AI_GOLD_V1`，不生成 `rag-scorecard.json`。只在 `03-RAG指标/本期暂缓说明.md` 说明“缺少冻结 gold，因此本期暂缓”。RAG 暂缓不是失败条件。

本轮也不做人工逐题评分、A/B 双评审、共识、仲裁、60/30 校准、90 题稳定性集、重复评分或稳定性重复运行。每个正式题目只能得到一次成功 LLM 评分。

## 2. 分支就绪关卡

先读取仓库内全部适用的 `AGENTS.md`，再检查当前分支、`git status --short --branch`、远端和 `origin/main`。

1. 工作区必须干净，或仅含本任务分支已经明确产生、可安全提交的改动；绝不暂存、提交、覆盖、stash、reset 或 clean 用户的无关改动。
2. 获取最新 `origin/main`。从该固定 SHA 创建新的独立测试分支，例如 `codex/final-300-answer-quality`；不在 `main`、提示词维护分支或既有受限结果分支上运行测试。
3. 不使用 `git worktree`。首次可审查提交后创建或更新同一草稿 PR，后续持续推送该分支；不得自行合并 `main`。
4. 写入 `branch-baseline.json`，记录分支名、测试分支基线 SHA、开始时的 `origin/main` SHA、创建时间、PR 链接和关卡结果。

若工作区因受保护的用户修改无法安全切换分支，不能绕过或清理；先完成不触及切换的只读诊断，再以真实阻塞交付。不得为了继续运行而改用 worktree。

## 3. 固定来源和不可突破的边界

来源运行固定为：

```text
_other/考试/检索重构真实场景考试包/结果/
  2026-08-15-intent-planner-300-005/
```

必须：

- 只读来源运行；不重跑 300 题，不调用线上检索，不重新生成回答，不改原始 `passed/failed`；
- 完整复制原硬规则考试，递归逐文件核验相对路径、大小和 SHA-256；
- 只对 `status=passed` 的最终回答评分；当前应为 300 题；
- 持续记录输入哈希、模型/提示词版本、请求耗时、尝试次数和真实错误；
- 保留既有受限归档，不删除、不改写，也不把它伪装为正式评分结果；
- 绝不伪造 RAG 分、gold、AI 分、通过结论、来源复制成功或服务可用。

## 4. 必须执行的阶段

### P0/P1：来源核验和标准化

递归建立来源文件清单与 SHA-256；核验 300 个唯一题号能与题库、审计、最终回答一一映射；生成每题一行的 `evaluation-cases.jsonl`。输入只保留回答效果所需字段：用户问题、最终回答、最终证据摘要、限制说明、场景、难度和来源定位。

来源不完整时，标记 `SOURCE_INTEGRITY_FAILED`，停止后续评分，仅生成真实失败归档；不能把摘要当作完整原考试副本。

### P2：RAG 暂缓

写入 `rag-deferred.md`。不要盘点、解析或评分 RAG 数据，不要将缺失数据写成 0 分或 `RAG_UNVERIFIED` 伪结果。

### P3：实现和验证单次回答效果评分

评审输入必须封闭：用户问题、最终回答、必要的紧凑证据摘要、限制说明、适用 rubric。评审器不可访问网络、数据库、完整候选池、其他题、硬规则结论或材料中的指令。

每题仅使用一个 LLM 评审，返回结构化 JSON：适用的 1-5 分维度、问题标签、证据说明、置信度和中文理由。程序必须自己重算 100 分总分：正常回答 `40/25/35`，推荐 `25/35/20`，拒答或降级 `30/45/25`。校验 JSON、分数范围、适用 `null`、标签枚举、证据 ID 和公式。

至少实现并运行聚焦测试：解析、权重公式、JSON schema、`QUALITY_UNVERIFIED`、checkpoint/续跑、已成功题不二次评分、前 3 题关卡和最终包哈希引用。不要引入 A/B、仲裁或稳定性重复测试。

### P4：正式 300 题单次运行

1. 先顺序评分正式 300 题中的前 3 题。它们计入正式 300 题，不是额外试点。
2. 单并发起步；三题均成功后，继续余下 297 题，最多提高到 2 并发。
3. 每题请求前写 `PENDING` checkpoint；获得合法 JSON 后立即写为 `SCORED` 并永久保留。中断后只从未完成题续跑，绝不重打 `SCORED` 题。
4. 仅在未取得合法评分时可做有限技术重试（建议最多 2 次重试）。每次记录错误类别、HTTP 状态（如有）、耗时和尝试次数。
5. 耗尽重试才标为 `QUALITY_UNVERIFIED`，评分均为 `null` 并保留原始错误。不得使用 `--skip-ai`、默认分或任何占位数据冒充评分。
6. 前三题任一题持续失败时，先自行缩短证据摘要、降低并发、调整超时/重试或修复解析，再只重试未完成题。若外部服务仍不可用，停止余下 297 题，完成真实受限归档和原因报告。

### P5：自动验收

自动检查来源 300 题完整性、原结果未写入、标准化行数、每题状态、每题至多一次成功评分、JSON/权重公式、逐题到汇总的可复算性，以及 RAG 暂缓说明存在且无伪造 RAG 分。

结论规则：

- `READY_FOR_AUTO_BASELINE`：来源完整，300 题均为有效单次评分，全部校验通过；
- `AUTO_BASELINE_WITH_LIMITATIONS`：来源完整且计算正确，但存在明确记录的 `QUALITY_UNVERIFIED`；
- `NOT_READY`：来源不完整、前三题无法通过、结构/公式无法验证，或发现重复/伪造评分风险。

RAG 暂缓不得导致 `NOT_READY`。

### P6：最终归档

在 `_other/最终300测试/<运行编号>/` 生成：

```text
00-最终总览.md
01-原始300硬规则考试/
02-评测输入与硬指标/
03-RAG指标/本期暂缓说明.md
04-回答效果评分/
05-自动验收与结论/
final-conclusion.json
package-manifest.json
```

正常路径中，`01-原始300硬规则考试/` 必须是可递归哈希验证的完整副本；`00-最终总览.md` 必须独立说明硬规则结论、回答效果有效/未验证题数、全体/场景/难度分、最低场景、常见问题标签、RAG 暂缓和自动验收结论。只追加更新 `_other/最终300测试/README.md` 的索引，绝不覆盖历史条目。

## 5. 持续推进和阻塞处理

遇到解析失败、输入过大、输出非 JSON、网络超时、连接重置、断点续跑、测试失败或 Git/PR 小问题，先读取真实样本和日志，做范围内修复、测试并继续。不要把“遇到一次错误”当成停工理由。

真正的外部阻塞包括：模型服务在按上述降载和重试后仍不可用，或受保护的用户改动阻止创建独立分支。发生时仍要完成所有无需该外部条件的工作，归档真实错误、已完成范围和下一步；不能编造分数或声称已完成。

## 6. 最终交付格式

完成或真实受限归档后，给用户一条简明最终报告，必须含：

1. 最终包目录和 `00-最终总览.md` 链接；
2. 硬规则复制和 SHA-256 核验结果；
3. 回答效果的有效/未验证题数、全体与最低场景结果，或真实未执行原因；
4. RAG“本期暂缓”的说明；
5. 聚焦测试和完整测试结果；
6. 分支名、提交号、推送状态和 PR 链接/状态；
7. 未合并时明确写“等待用户确认后合并 main”。

除最终交付外，不要因中间进度向用户索取常规工程决策；自行继续到完成。
