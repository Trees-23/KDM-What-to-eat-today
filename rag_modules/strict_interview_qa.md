# 基于 GraphRAG 的智能烹饪问答系统

## 严格面试官深度拷问题库

说明：

- 这份题库基于当前代码实现整理，重点覆盖 `graph_rag_retrieval.py`、`hybrid_retrieval.py`、`intelligent_query_router.py`、`graph_data_preparation.py`、`milvus_index_construction.py`、`session_cache_manager.py`、`web_service_handler.py`、`main.py`。
- 问题按“高压面试官”口吻设计，答案按“可自洽、尽量贴代码、不过度吹嘘”的标准整理。
- 遇到没有严格测试或没有量化数据的地方，建议答法是：承认不足、解释原因、给出后续测试方案。不要编造指标。

## 0. 先背熟的总述

### Q1：你这个项目一句话到底是什么？
A：这是一个面向菜谱推荐与烹饪问答场景的 GraphRAG 系统。核心思路是把菜谱、食材、烹饪步骤组织成知识图谱，同时保留向量检索链路，再通过路由模块根据查询特点选择传统混合检索、图RAG检索或组合检索，重点解决传统纯向量检索在复杂关系推理和结构化问答上的不足。

### Q2：你这个项目的核心创新点是什么？不要泛泛而谈。
A：核心不是“用了图数据库”，而是把查询分成不同检索范式来处理。简单说有四点：一是图RAG能做多跳关系和子图抽取；二是传统检索不是纯向量，而是实体级、主题级、向量级三路协同；三是路由模块不是固定走一条链，而是支持图RAG、传统和组合策略分流；四是服务层做了会话级缓存和流式返回，保证工程上可交互。

### Q3：你为什么要做 GraphRAG，而不是只做向量检索？
A：因为这个场景里很多问题天然是关系型问题，比如“鸡肉配什么蔬菜”“某个菜属于什么菜系”“一个食材通过哪些菜谱和哪些步骤发生关联”。纯向量检索能处理相似文本，但不擅长显式地走关系链。图RAG的价值是把“节点-关系-路径”作为可检索对象，把隐含关系变成显式证据。

### Q4：你这个项目的整体链路是什么？
A：先从 Neo4j 读取 Recipe、Ingredient、CookingStep 等节点，构建菜谱文档并切片；再用 HuggingFace Embedding 生成向量写入 Milvus；检索阶段有两大引擎，一个是传统混合检索，一个是图RAG检索；路由模块先分析 query，再决定走传统、图RAG或组合链路；最后把召回结果送入生成模块做答案生成，服务端再包一层缓存、上下文增强和流式输出。

## 1. 项目描述与架构设计

### Q5：你的项目为什么选“菜谱、食材、步骤”做图谱建模？
A：因为这三类实体已经能覆盖烹饪场景里最核心的关系结构。菜谱和食材之间有 `REQUIRES`，菜谱和步骤之间有 `CONTAINS_STEP`，菜谱和分类之间有 `BELONGS_TO_CATEGORY`，步骤之间可能有顺序关系。这个建模能支撑做法指导、搭配问答、分类问答和多跳推理。

### Q6：为什么你的图谱不是只建菜谱和食材，还要保留步骤节点？
A：因为很多问答不是“是什么”，而是“怎么做”。如果没有步骤节点，图里只剩静态关系，无法支撑流程型问题。保留 CookingStep 后，至少可以回答某道菜有哪些关键步骤，或者从食材如何连接到制作过程。

### Q7：为什么系统里同时要有图检索和向量检索？不是重复建设吗？
A：不是重复，而是互补。图检索更适合显式关系问题，向量检索更适合模糊语义问题，比如“推荐几个下饭菜”“想吃清淡一点的”。图检索强调结构，向量检索强调语义相似，组合起来覆盖面更完整。

### Q8：为什么还需要 BM25 或图索引键值对这种传统召回方式？直接 embedding 不行吗？
A：embedding 对模糊语义好，但对实体名、分类词和明确关系词不一定稳定。比如具体菜名、具体食材、明确主题词，传统关键词召回和图索引的确定性更高，所以保留了实体级和主题级的图索引召回链路。

### Q9：你这个系统的最关键模块是哪一个？
A：如果按算法价值看，是 `graph_rag_retrieval.py`；如果按系统稳定性看，是 `intelligent_query_router.py`，因为它决定了 query 先走哪条链；如果按工程闭环看，是 `main.py` 和 `web_service_handler.py`，它们把各模块串起来。

### Q10：你的系统是不是过度设计了？路由、图检索、混合检索、缓存、流式全上了。
A：从最小可用的角度看，确实比一个纯向量问答系统复杂。但这是为了验证不同检索范式在真实问答里的分工，而不是单纯堆功能。这个项目的价值不在“最小代码量”，而在“把结构化检索和语义检索的边界讲清楚”。

## 2. 图数据准备与建模

### Q11：你图数据准备模块具体做了什么？
A：`graph_data_preparation.py` 主要做三件事：第一，从 Neo4j 读取 Recipe、Ingredient、CookingStep 节点；第二，给 Recipe 额外挂接分类、食材和步骤信息，拼成更完整的文档内容；第三，对这些文档做分块，供向量索引和检索模块使用。

### Q12：为什么在文档构建阶段把图里的信息又转成文本？这不是“图退化成文”吗？
A：这是刻意的。生成模块最终消费的是文本上下文，所以图中的结构化关系要在检索阶段被翻译成高信息密度文本。这个思路能减少生成层拼 prompt 的复杂度。图的价值主要体现在“怎么检索”和“检索出什么结构证据”，不是强迫生成模块直接吃图结构。

### Q13：你菜谱文档里包含哪些信息？
A：包含菜品名称、描述、菜系、难度、准备时间、烹饪时间、份量、食材列表、步骤列表、标签等。也就是说 Recipe 文档不是裸节点，而是已经把一阶邻居信息融合进去了。

### Q14：为什么你把分类信息从关系里读，而不是只读节点属性？
A：因为图谱里分类信息可能同时存在于节点属性和关系结构里。代码里优先从 `BELONGS_TO_CATEGORY` 读分类，如果没有再回退到 `r.category`。这可以兼容图谱数据不完全规范的情况。

### Q15：你的文档切片策略是什么？
A：优先按二级标题 `##` 切，保留业务结构；如果没有明显章节，再按固定长度切，并保留 overlap。具体来说，短文档不切，长文档优先按章节切，如果章节结构不明显，就按 `chunk_size` 和 `chunk_overlap` 做滑动窗口切片。

### Q16：为什么不用更复杂的语义切片，而是按标题和长度切？
A：这个场景里的原始文档本身就带明显结构，比如“所需食材”“制作步骤”，按业务结构切比纯语义切片更稳定，也更容易解释。复杂语义切片不是不能做，而是当前版本优先保留可控性和实现简单度。

### Q17：这种切片方式有什么缺点？
A：缺点是跨章节信息可能被拆开，固定长度切片时也可能截断语义边界。尤其当步骤描述很长时，chunk 的完整性不一定最优。这个问题如果后续继续优化，可以改成按步骤节点天然分片或者 small-to-big 检索。

### Q18：你如何保证切片后的 metadata 对后续检索有用？
A：切片时保留了 `node_id`、`recipe_name`、`node_type`、`category`、`cuisine_type`、`difficulty`、`parent_id`、`chunk_id`、`chunk_index` 等字段，这些字段后面用于 Milvus 检索结果回填、去重、邻居增强和结果展示。

### Q19：如果面试官问你“为什么 chunk overlap 设成 50”，你怎么答？
A：当前值更像经验参数，不是严格调优后的最优值。它的目的是避免硬切片造成上下文断裂，同时又不让冗余过大。如果要严谨，我会说这个参数应该通过离线评测集调，而不是拍脑袋固定。

### Q20：你对切片做过评估吗？
A：当前代码里没有完整的切片离线评测，这是短板。更严格的做法应该构造一批典型问答，看不同切片策略对 Top-K 命中率和最终回答质量的影响。当前版本主要是先把结构化切片链路打通。

## 3. 向量索引与 Milvus

### Q21：为什么选 Milvus？
A：因为它对向量检索支持成熟，适合做结构化 metadata 过滤和相似度搜索，跟这个项目里“文本块 + metadata”的检索模式比较匹配。

### Q22：为什么选 HuggingFace Embedding，而不是直接调用线上 embedding API？
A：当前实现更偏本地化和可控性，使用 `HuggingFaceEmbeddings` 可以避免每次嵌入都依赖外部服务，降低成本和网络依赖。同时 embedding 模型和生成模型解耦，方便独立替换。

### Q23：你为什么选中文 embedding 模型？
A：因为场景是中文菜谱问答，菜品名、食材名、描述、主题词都高度中文化，中文 embedding 更匹配语义空间。当前默认是 `BAAI/bge-small-zh-v1.5`。

### Q24：为什么 schema 里要保留这么多 metadata 字段？
A：因为后续不仅要做相似度召回，还要做显示、过滤、去重、邻居增强和生成结果组织。向量本身只负责召回，真正让结果可用的是 `node_id`、`recipe_name`、`node_type`、`category` 这些 metadata。

### Q25：你为什么每次构建索引时都 `force_recreate=True`？
A：这是一个明显偏离线重建的设计，不适合生产在线更新。这样做是为了避免 schema 演进和脏数据兼容问题，保证当前构建结果干净一致。真实线上系统应该支持版本化集合、蓝绿切换或增量更新。

### Q26：你如何理解 Milvus 检索分数？
A：这块要非常谨慎。代码里对 score 和 distance 的处理存在约定风险，不能想当然说“越大越像”或“越小越像”，必须以具体 metric 和 SDK 返回语义为准。面试时最好承认这块需要配套校验和单测，而不是硬讲。

### Q27：你给向量检索结果做了什么增强？
A：在 `vector_search_enhanced()` 里，我会根据 `node_id` 回图库里取邻居节点，把邻居名补到文本里，形成“语义相似结果 + 图邻居增强”的上下文，这样最终给 LLM 的内容更丰富。

### Q28：为什么向量检索不是最终结果，而只是混合检索的一部分？
A：因为它擅长模糊语义，不擅长精确关系和显式结构。项目目标不是证明 embedding 无敌，而是把向量检索放到它最合适的位置，作为语义补充而不是唯一答案来源。

### Q29：你如何回答“维度写死 512 会不会有问题”？
A：会有问题，尤其换模型时。当前实现依赖默认模型恰好是 512 维，这不够鲁棒。更工程化的做法应该是在初始化时实际 probe 一个向量，自动校验模型输出维度和 schema 一致。

### Q30：你有没有做过向量召回的过滤？
A：代码支持 filters 参数拼接表达式，但当前主链路没有大量使用复杂过滤，更偏直接做语义相似召回。如果进一步优化，可以按 `category`、`node_type`、`difficulty` 等做前过滤，缩小候选空间。

## 4. 图索引与双层混合检索

### Q31：什么叫“实体级/主题级 与 向量级”混合检索？
A：这里不是简单把 BM25 和向量拼起来，而是把传统检索再拆成两层。实体级面向具体实体名，比如具体菜品、食材、工具；主题级面向抽象主题，比如减脂、川菜、下饭、快手。再加上一条向量级语义相似检索，三路互补。

### Q32：图索引键值对是怎么设计的？
A：在 `graph_indexing.py` 里，每个实体和关系都被转成 `(key, value)` 形式。实体的 key 主要是名称，value 是实体详情；关系会生成多个 key，比如关系类型、主题词、源实体主题词、目标实体名等，用来做更灵活的主题召回。

### Q33：为什么关系要生成多个索引键？
A：因为关系查询天然有多种入口。用户可能问“食材搭配”“烹饪过程”“菜品分类”，这些都不一定直接对应节点名，而是关系层的主题。给关系加多个 key，本质上是让关系也可被索引和检索。

### Q34：为什么关系索引键里还可能用 LLM 做增强？
A：目的是补充“人工规则很难枚举全”的全局主题词，让关系可以挂上更自然语言化的检索入口。不过这部分是可选开关，不是强依赖。

### Q35：为什么实体只用名称作为唯一索引键，会不会太弱？
A：是有局限的。它能保证确定性和简单度，但别名、多称呼、同义词覆盖不足。当前版本用名称做主键，属于“先保证精确召回”，后续如果做得更完整，应该引入别名、标准化和同义词扩展。

### Q36：你为什么还要对图索引做去重？
A：因为图谱里可能存在名称重复的实体，或者同一个源-目标-关系类型重复出现。去重可以减少索引膨胀，也避免同一信息在召回结果里反复出现。当前实体按名称去重，关系按 `source-target-type` 去重。

### Q37：你这个图索引去重会不会误伤？
A：会有可能。比如两个不同节点同名，但语义并不完全相同，按名称去重可能会过度合并。所以这是一种偏工程简化的处理，不是完美方案。更严谨的做法是先标准化实体类型和别名，再决定是否合并。

### Q38：实体级检索具体怎么做？
A：先根据 LLM 提取的 `entity_keywords` 从图索引里查实体，再根据命中的 `node_id` 去 Neo4j 拉一跳邻居做内容增强；如果结果不足，再走 Neo4j 的全文索引补召回，最后按分数排序返回。

### Q39：主题级检索具体怎么做？
A：先根据 `topic_keywords` 从关系键值对里查主题相关关系，再把关系两端的实体信息补到结果里；同时还会尝试按实体分类信息查相关 Recipe；如果还不够，再用 Neo4j 里对 `category/cuisineType/tags` 的匹配做补充召回。

### Q40：为什么主题级和实体级都要保留 Neo4j fallback？
A：因为图索引是内存里的轻量索引，可能不完整，也可能没覆盖所有 query 表达。Neo4j fallback 是补召回链路，防止图索引结果太少时直接没东西返回。

### Q41：你怎么保证双层检索结果不重复？
A：在 `dual_level_retrieval()` 里先把实体级和主题级结果合并，再按 `node_id` 去重，保留最高分那份。这样能避免同一道菜同时被实体级和主题级重复塞进最终结果。

### Q42：为什么混合检索的最终融合用的是 Round-robin，而不是统一排序？
A：因为几路结果的分数语义并不一致。实体级、主题级、向量级的分数来源不同，直接硬拼排序并不可靠。Round-robin 是一种简单、可解释的融合 baseline，能保证不同来源都有曝光机会。

### Q43：Round-robin 有什么问题？
A：问题是它没有真正做跨来源质量比较，可能把质量较差的一路结果也过早抬进前排。所以它适合作为早期融合器，不适合作为最终最优方案。

### Q44：你如何解释 `search_method`、`final_score` 这些统一 metadata？
A：这是为了让后续模块不用感知每路检索的细节。统一 metadata 后，日志、展示、调试和生成模块都能更容易看懂结果来源和大致得分。

### Q45：你有没有做过多路检索的分数归一化？
A：没有严格做。当前更像“按来源内排序 + 跨来源轮询合并”，不是标准的分数融合系统。如果被问到，我会明确承认这部分还停留在可用 baseline，而不是学习排序或严格分数校准。

## 5. 图谱推理检索

### Q46：你所谓“图谱推理检索”具体包含哪些步骤？
A：主要是四步：第一，用 LLM 解析 query 的图结构意图，输出 query type、源实体、目标实体和深度；第二，根据 query type 执行多跳遍历或子图抽取；第三，把节点、关系、路径序列化成高信息密度文本；第四，根据关系模式组织出推理链，提升可解释性。

### Q47：为什么图查询规划要交给 LLM？
A：因为用户 query 是自然语言，尤其在中文口语场景里，单靠规则很难稳定区分“这是在问直接关系、多跳关系还是子图主题”。LLM 的价值是把 query 转成更接近图查询结构的中间表示。

### Q48：这种设计最大的风险是什么？
A：最大的风险是结构化输出不稳定。当前实现里 LLM 直接返回 JSON，解析失败就走 fallback，这说明关键决策层确实依赖模型格式遵循能力。后续更稳的做法应该是 schema 约束或 function calling。

### Q49：你图查询里支持哪些类型？
A：枚举上有 `ENTITY_RELATION`、`MULTI_HOP`、`SUBGRAPH`、`PATH_FINDING`、`CLUSTERING`。但从实际实现完成度看，核心完成的是 `MULTI_HOP` 和 `SUBGRAPH`，`ENTITY_RELATION` 和 `PATH_FINDING` 的底层辅助方法还是空实现。

### Q50：如果面试官抓住“你有类型但没实现”怎么办？
A：不要硬扛，直接承认接口设计超前于实现进度。可以说当前闭环重点是多跳路径和子图提取，其它类型是预留接口，下一步需要补齐或者在路由阶段禁用，避免能力描述超出真实实现。

### Q51：多跳遍历是怎么做的？
A：以 source entity 为起点，在限制深度内找路径，收集 path、nodes、relationships，并用启发式公式给路径打分。评分因子主要包括路径长度、节点连通度和关系类型匹配情况，然后按分数排序返回路径结果。

### Q52：为什么路径评分要考虑路径长度？
A：路径越短，通常语义链越紧，噪声越少。长路径虽然能连得更多，但更容易把弱相关节点卷进来，所以短路径在图检索里通常更可信。

### Q53：为什么又考虑节点度数？高连接节点不一定更相关啊。
A：这是启发式假设，不是绝对真理。高连接节点往往是局部图里的桥接节点，能提供更丰富的上下文，但也可能是 hub 噪声。所以这只是一个早期排序特征，不是严格最优规则。

### Q54：子图抽取的价值是什么？
A：多跳路径更适合回答“从 A 到 B 怎么连”，子图抽取更适合回答“围绕某个主题有哪些相关知识网络”。比如问“川菜有什么特色”，比起给一条路径，更适合给一个局部知识子图再做总结。

### Q55：你为什么要做关系序列化？
A：因为如果只把路径里有多少个节点、多少条边告诉下游 LLM，信息几乎没法用。关系序列化把“起点-关系-终点-属性”都展开，LLM 才能真正理解这条路径在说什么。

### Q56：你的推理链到底是什么？是真正的逻辑推理吗？
A：严格说不是形式化推理，更像基于图模式的启发式解释生成。它会根据关系类型和节点标签识别“食材组成、步骤流程、分类归属、难度映射、相似特征”等模式，再转成可读的解释链。

### Q57：为什么你认为这种“启发式推理链”有意义？
A：因为生成模块最终需要的是可读上下文，而不是生硬的节点边列表。推理链能把图结构证据变成更像“解释”的文本，提高答案的可读性和用户感知到的可解释性。

### Q58：如果面试官说“这不是推理，只是模板生成”，你怎么答？
A：我会承认它不是严格逻辑推理，而是“基于图模式的可解释结构摘要”。项目里用“推理”这个词，更强调它利用了图结构关系而不是纯文本相似性，但从学术定义上它确实更接近 explainable graph summarization。

### Q59：图RAG返回给生成模块的是什么？
A：是 `Document` 列表，每个 `Document.page_content` 已经被组织成路径说明、子图摘要或推理链文本，metadata 里还带了 `search_type`、`path_length`、`relevance_score`、`node_count`、`relationship_count` 等辅助信息。

### Q60：你为什么不让生成模块直接消费图结构，而是提前组织成文本？
A：这样做的好处是把复杂度集中在检索层，生成层保持简单。当前生成模块只拼接 `Document.page_content`，不需要理解图对象。这种模块边界更清晰，但代价是损失了一些结构化控制能力。

## 6. 智能检索路由

### Q61：你的路由模块到底做了什么？
A：路由模块的职责是先分析 query 的特点，再决定走 `HYBRID_TRADITIONAL`、`GRAPH_RAG` 还是 `COMBINED`。分析结果里会有复杂度、关系密集度、实体数、推荐策略和解释理由。

### Q62：路由主路径是真正“按复杂度阈值计算”的，还是 LLM 直接给结果？
A：主路径里是 LLM 直接给 `recommended_strategy`，复杂度、关系密集度和实体数量更多是解释性字段。真正用这些值做规则判断的是 fallback 路径 `_rule_based_analysis()`。

### Q63：那你简历里如果写“基于复杂度和关系强度动态调度”会不会夸大？
A：如果写得很绝对，会有夸大风险。更准确的说法应该是：基于 LLM 的查询分析结果进行检索分流，并在模型不可用时使用规则方法根据复杂度、关系强度和实体数做降级分流。

### Q64：为什么要有 COMBINED 策略？
A：因为很多 query 不完全属于“图问题”或“非图问题”，比如既有明确主题又带关系色彩。两端硬切会损失召回，所以加一个中间态组合策略，让图检索和传统检索都参与。

### Q65：为什么 fallback 规则要专门对中文句式做处理？
A：因为中文查询里很多关键信号不靠分词，而靠句式，比如“配什么”“有什么关系”“从 A 到 B”“为什么”。如果只做关键词计数，很容易把需要图检索的问题误判成普通文本检索。

### Q66：你如何解释“规则化 fallback 提升鲁棒性”？
A：意思不是它一定让效果变更好，而是当 LLM 分析失败、格式异常或服务不可用时，系统仍然可以靠规则继续分流，不至于整条链路瘫掉。更稳妥的说法是“保障可用性”，而不是“显著提升效果”。

### Q67：你这个路由模块有没有做效果评估？
A：当前没有完整离线 benchmark，这是需要补的地方。严谨做法应该是准备一批 query，人工标注最合适策略，再评估路由准确率以及路由对最终回答质量的影响。

### Q68：如果面试官问“你凭什么说路由有价值”，怎么答？
A：可以从设计逻辑和工程收益答：一是不同 query 需要的检索范式不同，统一走一条链会浪费或失配；二是组合策略能降低单一路径失手的概率；三是 fallback 让系统在模型波动时还能继续工作。再补一句，目前主要是架构价值已验证，量化收益还需继续评估。

### Q69：你为什么不把路由和图查询理解合并成一次 LLM 调用？
A：可以合并，但当前拆开是为了职责清晰。路由关注“用哪种检索引擎”，图查询理解关注“进入图引擎后怎么走”。代价是多一次 LLM 调用和多一个不稳定源，后续可以合并为统一 retrieval plan。

### Q70：路由失败时的兜底策略是什么？
A：首先 `analyze_query()` 失败时会回退到 `_rule_based_analysis()`；其次 `route_query()` 执行异常时会整体降级到传统混合检索。也就是说先局部降级，再链路级降级。

## 7. 生成、幻觉与可解释性

### Q71：你的生成模块做了什么？
A：生成模块比较简单，职责是把检索得到的 `Document` 列表拼成上下文，然后用统一 prompt 调 LLM 生成回答。它不负责复杂的检索逻辑，尽量保持“消费检索结果”的角色。

### Q72：你如何处理幻觉？
A：严格说，当前系统没有做非常强的抗幻觉机制，比如证据级引用约束、answer verification 或 self-check。现有做法主要是两点：一是尽量提升召回证据质量，尤其把图关系和路径展开；二是在 prompt 里提醒“基于已检索信息回答，不要凭空添加”。这能缓解，但不能彻底杜绝幻觉。

### Q73：如果面试官追问“这不算处理幻觉”，你怎么答？
A：我会承认当前更偏“降低幻觉风险”，还不是强约束。真要往严谨方向做，可以增加引用式回答、证据对齐校验、拒答策略或 answer reranking。现在这版重点在检索增强，而不是严格事实校验。

### Q74：图RAG为什么会比纯向量方案更可解释？
A：因为图RAG返回的是“路径为什么连上”“有哪些关键关系”“哪些节点构成局部网络”，解释天然带结构证据。纯向量检索通常只能说“这段文本相似”，很难说清关系链本身。

### Q75：你为什么把图推理链放进 `page_content`，而不是 metadata？
A：因为生成模块主要拼接 `page_content`，所以要把关键信息直接放到文本主体里，确保下游 LLM 一定能看到。metadata 更像辅助字段，不适合承载必须被模型消费的信息。

### Q76：你的 prompt 为什么这么简单？
A：因为这个项目把复杂度尽量前移到了检索层。检索结果如果已经足够清晰，生成 prompt 可以保持简单统一。这样也有利于后期对比“检索质量变化”而不是“prompt 魔法变化”。

### Q77：你有没有做过答案质量测试？
A：当前没有系统化自动评测，这个需要补。比较合理的做法是人工构造一批问题，标注标准答案或关键事实点，然后评估检索命中率、答案事实正确率和可解释性。

## 8. 性能优化、缓存与流式响应

### Q78：为什么要做会话级语义缓存？
A：因为多轮对话里用户很容易重复问相似问题或者追问近义问题。如果每次都重新检索和生成，成本高、延迟也高。会话级语义缓存可以在 session 维度复用相近 query 的结果。

### Q79：为什么缓存是按 session_id 隔离的？
A：因为同样一句 query 在不同会话上下文里可能含义不同。按会话隔离能减少跨用户串语义，也更符合多轮对话的上下文依赖。

### Q80：你缓存命中的依据是什么？
A：对当前 query 和会话内历史 query 做 embedding，相似度超过阈值 `0.75` 就认为命中缓存，直接返回历史 response。

### Q81：为什么阈值是 0.75？
A：当前是经验值，不是严格调优结果。它的含义是在“避免误命中”和“尽量提高复用率”之间取一个折中。更严谨的做法是准备相似/不相似 query 对，调这个阈值的 precision-recall。

### Q82：你这个缓存最大的风险是什么？
A：最大风险是误命中，也就是 query 表面相似但实际上问的不是同一个问题，直接复用旧回答会造成严重答非所问。尤其当前还把上下文增强 query 和原 query 分开处理，这就更需要谨慎。

### Q83：你为什么在缓存命中后还要把结果写入上下文？
A：因为缓存命中本质上也是一次有效交互，后续多轮对话可能依赖这轮问答内容，所以仍然要写入 session context，保持上下文连续性。

### Q84：上下文增强是怎么做的？
A：取最近最多三轮对话，把“用户问”和“AI答”的摘要拼到当前 query 前面，再把增强后的 query 送去路由和检索。这样可以让多轮省略式提问保留上下文信息。

### Q85：为什么只取最近三轮？
A：因为上下文越长越容易引入噪声，也会增加 prompt 长度和检索偏移。当前取三轮是个轻量折中，既保留最近上下文，又避免 query 被历史对话淹没。

### Q86：为什么缓存检查和 query 预处理要并行？
A：因为它们彼此独立，都发生在正式检索前。并行后，如果缓存命中可以更快返回；如果缓存未命中，也不会额外浪费时间去串行等待上下文增强。

### Q87：你如何解释 SSE 流式响应的价值？
A：流式响应不一定降低总耗时，但能降低用户感知延迟，尤其在 LLM 生成较慢时更明显。用户更早看到输出，交互体验更好。

### Q88：你的流式缓存命中为什么按 3 个字符切块返回？
A：这是一个很工程化的展示策略，不是算法核心。目的是让缓存命中也保持和实时生成类似的流式体验，避免前端状态逻辑分叉太大。

### Q89：如果面试官问你“有没有测过性能提升”，你怎么答？
A：如果没有实测，不要编。诚实答法是：目前做了缓存、并行预处理和流式响应这些优化点，从设计上能降低重复计算和感知延迟，但还没有形成严格的线上压测和命中率报表。后续应补缓存命中率、P50/P95 时延和首 token 延迟统计。

### Q90：你如果真要测性能，会怎么测？
A：分成三层测：一是检索层，测传统检索、图RAG、组合检索各自耗时；二是服务层，测缓存命中与未命中的端到端时延、首 token 时间；三是整体层，用固定 query 集做并发压测，记录 P50/P95 延迟、错误率和缓存命中率。

## 9. 兜底、异常与鲁棒性

### Q91：你系统里有哪些兜底策略？
A：主要有六类：一是图查询理解失败时降级成默认子图查询；二是路由分析失败时走规则分析；三是路由执行失败时整体降级到传统混合检索；四是图索引和主题/实体召回不足时有 Neo4j fallback；五是流式生成失败时切回非流式生成；六是各种数据库或模型异常时多数模块会返回空结果而不是直接崩。

### Q92：这些兜底策略的代价是什么？
A：代价是质量可能明显下降，但系统可用性提高。比如 LLM 解析失败后把整句 query 当成 source entity，本质上只是保底，不是高质量方案。

### Q93：为什么代码里这么多 `except Exception`？
A：这是集成型原型常见的问题，优先保证链路不断，但牺牲了错误可观测性。更成熟的系统应该把异常拆成模型输出解析错误、图查询错误、向量检索错误、网络错误等，并打出更细的监控指标。

### Q94：如果 Neo4j 挂了会怎么样？
A：图RAG和图索引增强会受影响，传统混合检索里的图相关部分也会退化。当前系统里，如果图连接没建起来，图RAG会返回空，最终更多依赖向量检索和传统 fallback。严格说这不是完全高可用，只是尽量不整站崩。

### Q95：如果 Milvus 挂了会怎么样？
A：向量召回会失效，传统混合检索会少一条语义链路，但实体级和主题级图索引召回、图RAG路径和子图检索仍然可以工作。也就是说系统还能答，但模糊语义问题会受影响更大。

### Q96：如果 LLM 挂了会怎么样？
A：影响最大。路由分析、关键词提取、图查询理解、最终生成都会受影响。当前只有分析和检索入口有一定规则 fallback，最终生成没有真正本地兜底，所以 LLM 是关键依赖。

### Q97：你如何回答“这个系统最脆弱的地方是什么”？
A：最脆弱的是关键决策层对 LLM 结构化输出的依赖比较重，而 schema 约束和评估闭环又不够强。这会影响路由稳定性、图查询稳定性和关键词抽取稳定性。

## 10. 测试、指标与量化

### Q98：你有没有做过召回率测试？召回率是多少？
A：如果没有做过，就必须诚实说没有完整离线召回率评测。当前项目更多是功能验证和架构验证，缺系统化指标。然后补一句：如果要测，我会先按问答类型构造测试集，标注每个 query 的 gold evidence 或 gold recipe，再评估 Top-K 命中率、MRR 和最终答案正确率。

### Q99：那你怎么证明这个项目真的比纯向量好？
A：如果没有量化结果，不能说“已经证明”。更稳妥的答法是：从设计上，图RAG对复杂关系问答更有优势，我也通过典型案例观察到路径和子图结果更适合回答关系型问题，但还需要系统化 A/B 测试来量化。

### Q100：如果让你今天补一套评测，你会怎么设计？
A：我会把 query 分成四类：实体查找、主题问答、关系问答、流程问答。每类抽取一批 query，人工标注 gold evidence。然后做三组实验：纯向量、传统混合、图RAG/路由系统。指标看 Top-K evidence 命中率、最终答案事实点覆盖率、人工可解释性评分和平均延迟。

### Q101：你会怎么测缓存收益？
A：准备一批真实多轮 query 序列，统计缓存命中率、命中后端到端时延下降、命中误答率，以及缓存命中与未命中的用户满意度差异。

### Q102：你会怎么测路由效果？
A：先人工给 query 标注“最适合的检索策略”，算路由正确率；再测 route 后的 downstream answer quality，看 route 是否真的提升最终效果，而不是只看路由本身是否和人工一致。

### Q103：你会怎么测图RAG的效果？
A：对关系型 query 建一组专门测试，比如搭配、分类、流程、相似菜谱、跨实体多跳问题。评估路径/子图是否命中关键证据，以及最终回答是否包含正确关系链。

### Q104：如果面试官问“你没做指标还敢写简历亮点？”怎么答？
A：我会说：当前亮点描述的是实现能力和架构设计，不是量化结论；凡是没有严格测试支持的地方，我不会在简历里写“显著提升 X%”。这既诚实，也更不容易被追着打。

## 11. 代码实现细节

### Q105：你的 `GraphRAGRetrieval.initialize()` 做了什么？
A：连接 Neo4j，测试连接，再构建一个轻量图结构缓存，包括高频实体和关系类型统计，用于后续查询加速和调试。

### Q106：为什么 `_build_graph_index()` 只取 1000 个实体？
A：这是性能上的折中，优先构建高连接度实体的轻量缓存，不追求全量缓存。好处是初始化快，坏处是覆盖不全，只适合作为辅助索引而不是完整索引。

### Q107：`understand_graph_query()` 输出哪些字段？
A：输出 `query_type`、`source_entities`、`target_entities`、`relation_types`、`max_depth`。这些字段组成 `GraphQuery`，作为图检索执行的中间结构。

### Q108：`adaptive_query_planning()` 和 `understand_graph_query()` 有什么关系？
A：从代码上看它们都属于“查询规划”思路，但主搜索链路实际用的是 `understand_graph_query()`，`adaptive_query_planning()` 更像保留的扩展接口，目前不是主执行路径。

### Q109：你的 `_parse_neo4j_path()` 做了什么？
A：把 Neo4j 返回的 path record 统一转成 `GraphPath`，同时把节点和关系都序列化成后续可展示、可生成的 dict 结构。

### Q110：你的 `_build_path_description()` 为什么要显式写“图路径概览”“关系明细”“推理结论”？
A：这是为了让下游 LLM 更容易读懂路径结果。比起把原始对象塞进去，结构化自然语言更适合生成模块直接消费。

### Q111：`_identify_reasoning_patterns()` 是怎么识别模式的？
A：它主要看关系类型集合，比如命中 `REQUIRES` 就判定有食材组成模式，命中 `CONTAINS_STEP/NEXT_STEP` 就判定有步骤流程模式，命中 `BELONGS_TO_CATEGORY` 就判定有分类归属模式。

### Q112：你的 `_validate_reasoning_chains()` 在干什么？
A：对生成的推理链做简单打分和去重，优先保留和 query 词项更相关、文本更完整的推理链，避免无关或重复的链全部送入最终上下文。

### Q113：`extract_query_keywords()` 为什么要区分 entity_keywords 和 topic_keywords？
A：因为查询里“红烧肉”“鸡胸肉”这种实体词和“减脂”“川菜”这种主题词适合走不同召回链路。拆开后，实体级和主题级检索都能更专注。

### Q114：`_get_node_neighbors()` 为什么只取名字？
A：因为这里的目标是低成本做结果增强，而不是把邻居整个子图拉回来。取邻居名能快速给结果补充一些相关上下文，但表达能力也相对有限。

### Q115：为什么 `hybrid_search()` 里 dual_docs 和 vector_docs 只各取 top_k？
A：这是个简化策略，避免候选集过大。更严谨的做法可能是每路取 `2*top_k` 再融合，给 rerank 更多空间。当前版本优先控制复杂度。

### Q116：你为什么在向量结果里把邻居补到文本后再交给 LLM？
A：这样能让语义相似结果附带一点关系背景，减少纯向量结果过于薄的问题。它本质上是用图谱给向量检索做轻量后增强。

## 12. 面试官最爱追的“为什么这么做”

### Q117：为什么图检索结果最终只返回 top_k=5？
A：因为问答场景里过多上下文会稀释有效证据，也会增加生成成本。当前更强调高密度少量证据，而不是长上下文堆叠。

### Q118：为什么图RAG和传统检索都返回 `Document`？
A：因为这样能统一接口，路由和生成模块不需要知道上游到底来自哪种检索器。`Document` 是一个很适合作为“中间交换格式”的抽象。

### Q119：为什么你不直接把 BM25 当主链路，而要搞图索引键值对？
A：BM25 对长文本块是全文相关性，图索引键值对更像实体/关系级索引，两者粒度不同。图索引键值对更容易对“具体节点”和“具体关系主题”做控制。

### Q120：为什么在推荐系统接口里直接随机取菜谱，而不是走 GraphRAG？
A：从当前代码看，推荐接口更像一个独立的 demo 功能，没有深度接入检索主链。这恰好说明项目的重点仍然是问答链路，不是完整个性化推荐。

### Q121：为什么你的图谱推理检索仍然需要 LLM 做生成，不能直接模板回答吗？
A：因为用户问法多样，召回结果也可能来自不同模块。模板适合回答非常结构化的固定问题，但不适合统一处理复杂、开放式和多证据问答。

### Q122：为什么你说项目解决了“复杂查询处理能力不足”的问题？
A：更准确的说法应该是“针对这个问题做了有针对性的架构设计”，而不是已经量化证明完全解决。项目通过图RAG、多路召回和路由机制，明显在设计层增强了复杂查询的处理能力。

## 13. 面试官会抓的风险点与诚实答法

### Q123：你有没有严格做过 AB Test？
A：没有完整线上 A/B。当前更偏本地功能验证和模块联调。后续如果继续迭代，我会优先补离线评测集和小规模人工对比实验。

### Q124：你有没有线上真实用户数据？
A：如果没有，就直接说没有。可以补一句：目前主要是开发和验证阶段，所以性能和效果评估更多依赖预设问答集和人工观察。

### Q125：你有没有做过真正的防幻觉测试？
A：没有系统化测试。当前只有检索增强和 prompt 限制，属于弱约束。下一步应该加证据引用和拒答逻辑。

### Q126：你有没有做过查询日志分析来优化路由词表？
A：如果没有，不要编。可以说当前 fallback 规则来自场景经验和 query 模式分析，但还没有基于大规模日志做迭代。

### Q127：你有没有做过缓存误命中分析？
A：如果没有，可以说当前只实现了相似度阈值命中机制，还没系统分析误命中 case。这会是后续需要补的质量保障项。

### Q128：你有没有测过 Neo4j 多跳遍历的性能瓶颈？
A：如果没有，可以说当前深度限制通常较小，更多靠控制 `max_depth` 和返回条数来约束开销，但还没有做系统性能 profile。

### Q129：为什么 `ENTITY_RELATION` 和 `PATH_FINDING` 没实现还写到枚举里？
A：诚实说是设计先行、实现未完全跟上。好处是接口层保留了扩展点，坏处是能力描述和真实交付之间有落差。

### Q130：你从这个项目里学到的最重要一件事是什么？
A：最重要的是，RAG 的关键不只是“换一个检索器”，而是明确不同问题的证据形式和最合适的召回范式。复杂查询不能指望一种检索策略包打天下。

## 14. 困难点与解决思路

### Q131：这个项目最难的点是什么？
A：最难的点是把图结构结果真正变成生成模块可消费的上下文。单纯把图查出来不难，难的是让“节点、关系、路径、局部子图”变成对问答有帮助、对 LLM 友好的证据文本。

### Q132：你是怎么解决这个困难的？
A：我把难点前移到图检索层：对节点和关系做统一序列化，对路径做摘要，对子图按标签和关系聚合，再补上启发式推理链。这样生成层不需要懂图对象，也能拿到结构化证据。

### Q133：第二个困难点是什么？
A：不同检索链路的分数不可比。实体级、主题级、向量级、图路径级的分数来源完全不同，直接统一排序很危险。

### Q134：你怎么处理这个问题？
A：当前用的是保守策略：各路内部先排序，跨路先做 Round-robin 融合，保证不同来源都有机会进入上下文。这不是最优，但比错误地强行统一分数更稳。

### Q135：第三个困难点是什么？
A：LLM 既负责 query 分析，又参与关键词提取和最终生成，容易成为全系统单点脆弱源。

### Q136：你怎么缓解这个问题？
A：通过多层 fallback 降低依赖强度，比如路由失败走规则分析、图查询理解失败走默认子图查询、流式生成失败切换非流式。虽然不能完全去掉依赖，但能减少链路直接中断。

### Q137：召回率是多少？

### Q139：缓存命中率多少？

### Q140：图RAG比纯向量提升了多少？
A：如果没有 benchmark，不要给百分比。可以答：在关系型 query 的 case 上，图路径和子图证据更贴题，但还需要系统化实验支持量化结论。

## 16. 最后 10 个杀伤力很强的追问

### Q141：你这个项目里，最像“工程补丁”而不是“干净设计”的地方是什么？
A：图结构返回格式不统一后，在 Python 侧做关系 flatten 和序列化补救；还有多路分数不可比时先上 Round-robin。这些都是“先跑通、再演进”的典型做法。

### Q142：如果让你重构一次，第一刀砍哪里？
A：先重构关键决策层，把路由分析、图查询理解、关键词抽取统一做成带 schema 约束的结构化输出，减少当前多处 `json.loads()` 和宽泛异常处理的脆弱性。

### Q143：如果只允许保留一个亮点写简历，你保留哪个？
A：我会保留“图谱推理检索”，因为这是项目最能体现结构化检索思路的地方，也最区别于普通向量问答系统。

### Q144：如果你投的是后端岗，不是算法岗，怎么讲这个项目？
A：会把重点放在系统分层、检索链路编排、缓存和流式响应、异常兜底、服务化接口设计，而不是只讲模型和图谱。

### Q145：如果你投的是大模型/RAG岗，怎么讲这个项目？
A：会把重点放在图RAG为什么存在、路由为什么必要、多路召回如何互补、结构化证据如何降低复杂关系问题的答非所问概率，以及当前还缺哪些评测和校验机制。

### Q146：你这个项目最大的不实之词风险是什么？
A：一是把启发式解释链说成“强推理”；二是把还没做完的 query type 说成已完整支持；三是把没有量化的体验优化说成“显著提升”。面试里要主动降调，才能站得住。

### Q147：如果面试官问“你到底写了什么核心代码”，怎么答？
A：我会说我主要参与了图RAG检索模块、混合检索链路、查询路由、图数据到文档的构造、Milvus 向量索引接入、会话缓存和流式 API 这几块，把结构化检索和语义检索串成了完整闭环。

### Q148：如果面试官问“这个项目最不像生产系统的地方是什么”，怎么答？
A：缺离线评测、缺细粒度监控、异常处理过宽、关键决策过度依赖 LLM、部分接口未完全实现。这些都说明它更偏高质量原型，而不是 fully productionized system。

### Q149：如果面试官说“你这个项目的路线是对的，但实现还比较初级”，你怎么接？
A：我会同意一半。路线确实是先把结构化检索、混合检索、路由和服务闭环搭起来，实现上还有很多从原型到产品的距离。我的优势在于我清楚问题在哪，也知道下一步优先补哪些环节。

### Q150：你准备怎么把这个项目讲成你的优势，而不是漏洞清单？
A：我的讲法会是：这个项目不是“我把 GraphRAG 吹得很神”，而是我在一个具体场景里认真拆解了图检索、向量检索、路由、缓存和流式交互的边界，做出了一个有完整链路、有明确问题意识、也知道自己短板在哪里的系统。面试官通常更信这种说法。

## 17. 复盘建议

建议你复习时优先准备下面 12 个主题：

1. 为什么纯向量检索不够，为什么需要图RAG。
2. 图谱里为什么选 Recipe / Ingredient / CookingStep 三类节点。
3. 文档构建为什么把图转成文本，切片为什么这么切。
4. 图索引键值对和实体级/主题级检索具体怎么做。
5. 向量检索在这个系统里扮演什么角色。
6. 图RAG的多跳遍历、子图抽取、路径说明和推理链怎么组织。
7. 路由模块主路径和 fallback 路径分别是什么。
8. 为什么要 COMBINED，为什么要 Round-robin。
9. 会话缓存、上下文增强和流式响应怎么做。
10. 当前系统怎么兜底，哪些地方还不够强。
11. 没做测试和没量化的地方要怎么诚实回答。
12. 如果重构，第一优先级改哪里。

如果你能把这 12 个主题讲顺，绝大多数严格追问都能扛住。
